# HTTP subscription live qualification

Use [ADR-0026](../adr/0026-http-subscription.md) for this checkout's fresh HTTP
subscription behavior. This procedure specifies evidence; it neither reports a
live pass nor authorizes live operations or publication.

For an ordinary recurring candidate, declare `mvp-http-recurring-live-v1` with
the existing `recurring-subscription-upgrade` scope and
`sbxr-subscription-update-v1` contract. Declare exactly one freshly verified
then-current stable source and preserve the existing signed attempt, unchanged
candidate assets, source support, runner/package facts, request/hash chain,
actual observations and validation/submission deadlines. The initial approved
incoming route remains the unchanged v3.1.81/159 source. A separately applicable
clean-install repair declaration may use `mvp-http-live-v1`; this does not widen
that repair scope's baseline/history restrictions.

The recurring order is:

1. `source-<tag>-precommit`: freshly prepare the exact source, including its
   supported subscription. Observe the actual precommit interruption and use
   its public Recover to restore the exact source.
2. `source-<tag>-upgrade`: update that source normally to the signed candidate.
3. `source-<tag>-postcommit`: reviewed removal and fresh source preparation;
   observe the committed interruption and candidate forward recovery.
4. `mvp-install`: reviewed removal to proved owned absence, then clean packaged
   candidate install/setup and genuinely outside REALITY proxy traffic.
5. `mvp-subscription`: confirm HTTP enablement and its interception/tampering
   disclosure. Prove outside authenticated HTTP on the emitted TCP 8443 link,
   exact one-node REALITY artifact, wrong-token refusal, protected local files
   and secret-safe captures, no certificate/renewal resources or Certbot install,
   actual Karing import, fresh node latency, manual refresh, and preserved
   selected client connection/settings.
6. `mvp-credentials`: retain all existing Client Identity/session revocation,
   replacement traffic, unchanged-link refresh, link rotation/old-link rejection
   and fresh Karing replacement-latency evidence.
7. `mvp-serving`: restart only the owned serving service through the supported
   ordinary systemd route. Verify the unchanged link and current artifact,
   outside authenticated HTTP, no certificate or renewal resources, and working
   proxy traffic. Do not manufacture a certificate replacement observation.
8. `mvp-removal`: retain ordinary restart/access proof, reviewed Complete
   removal, exact owned absence and outside rejection, unrelated-resource/SSH
   preservation, and actual client, process, capture and secret cleanup.

The collector emits the exact policy-specific checklist. Use the existing
`mvp-observe.py` recorder and `v3-mvp-evidence.py` assembler with original
timestamps and facts; never convert an old HTTPS observation into HTTP proof.
The public Acceptance Record explicitly discloses HTTP and its lack of transport
protection. Its normal immutable release/attestation trust remains required.

## Source compatibility and certificate capacity

Precommit interruption/recovery preserves exact source Ownership Record bytes,
provenance, both credentials, link and normally trusted HTTPS. Its check is
`outside-subscription-transport-preserved`. Upgrade/postcommit retain those
source proofs through updater transaction cleanup, then must complete HTTP
migration. For the unchanged v3.1.81 updater, exit its old menu after cleanup
and launch the newly installed `sudo sbxr` with no arguments. Observe the actual
new-root handoff; the private candidate runtime cannot perform it. New updater
code invokes the same handoff only after journal cleanup and runtime-exclusion
release. Prepared rollback never migrates.

Prove HTTP outside retrieval with the exact same IPv4, TCP 8443, path and token,
unchanged proxy UUID/configuration and process, and every retained certificate
byte/live link and creator identity. Prove owned renewal configuration/drop-in/
hooks quarantined, TCP 80 retired, official shared Certbot route/timer and
unrelated CA state preserved, zero migration issuance/renewal/revocation/deletion,
and no pending migration flag or publication staging. Retained
`https_retirement` cleanup authority must remain; it is not operation residue.
Display the replacement URL via confirmed View details, edit the existing
Karing profile URL and manually refresh while preserving profile, DNS, routing,
TUN and selector settings. Do not substitute removal/reinstall or replace the
client profile. An interrupted handoff resumes forward through the new root
launch or supported Recover, with no manual protected-state edit.

The v3.1.81 preparations before precommit and postcommit each obtain one
production subscription certificate through that unchanged source. The fresh
HTTP candidate's enablement and serving restart obtain none: budget **two**
issuances for this initial route, rather than four. Confirm fresh retained CA
capacity for those two before any live source setup. HTTP-to-HTTP recurring
qualification needs zero subscription issuances. Neither rate-limit timing nor
current VPS cleanliness is established by local tests.

The initial route uses the declared unchanged HTTPS source. Future source
readiness must establish its actual transport and any retained cleanup authority;
this initial legacy-source evidence does not itself prove an HTTP-source live
upgrade. No historical observation qualifies changed bytes.

## Retained safeguards and limits

Apply the non-certificate prerequisites, operator/outside/Karing attendance,
temporary qualification transport and protected-log-parent procedure, source
staging/trust checks, 30-minute scenarios, two-hour subscription journey,
five-minute submission/validation, no-prefix-publication rule, stop/burn handling
and actual safety/final cleanup from
[ordinary recurring acceptance](ordinary-recurring-live.md). Qualification
transport TLS, GitHub/asset TLS and software attestations remain separate.

Apply the non-certificate artifact, client, credential, disclosure and evidence
handling requirements from [MVP acceptance](mvp-live-acceptance.md). Its old
certificate-replacement procedure and trusted-subscription-TLS requirements
apply to legacy HTTPS policies only. Do not run CA dry runs, replacement or
renewal actions for a fresh HTTP candidate. Root-only isolated Linux/systemd
fixtures and native CI remain required where applicable; local fixtures do not
prove the VPS, outside route, real Karing's HTTP acceptance, or a live release.

Bearer-token protection prevents unauthenticated retrieval at the server.
Plain HTTP still lets a network observer steal the link and proxy UUID or alter
the downloaded configuration. No claim of secret containment on the network is
made. Preserve protections for local files, logs and retained evidence.
