## Startup: an ordinary serving start can block proxy authorization

The live restart command requested both units together:

```sh
systemctl restart sing-box.service sbxr-subscription.service
```

Fresh read-only journal extraction provides microsecond timestamps:

| UTC | Observation |
|---|---|
| 07:47:47.873841 | systemd reported the subscription process started. |
| 07:47:47.884104 | systemd began starting sing-box. |
| 07:47:48.241750 | sing-box was skipped because its ExecCondition refused. |

The subscription unit is `Type=simple`, so its started notification does not
establish that SBXR's startup checks or listener binding had completed.
The retained ExecCondition process exited 1. sing-box remained inactive with
`Result=exec-condition`; the outer restart command nevertheless returned 0.

The source contains the following interaction:

1. [`serveSubscription`](../../../internal/proxyinstallation/serving.go) acquires
   the existing whole-host lock before reading installed/ownership state and
   preparing the subscription. It releases that lock after listener binding.
2. [`AcquireSubscriptionReviewLock`](../../../internal/proxyinstallation/adapter/host/subscription.go)
   delegates to the existing mutation-lock implementation, which uses an
   **exclusive**, nonblocking `flock` even for this read-only startup work.
3. [`filesystemInspector.inspectLock`](../../../internal/softwarelifecycle/status_local.go)
   treats a held lock as `Update in progress`.
4. [`authorizeProxyStart`](../../../internal/proxyinstallation/client_identity.go)
   responds to that status by requiring the private runtime lock handoff.
   An ordinary systemd restart has no Owner operation lending that authority.
   Failed borrowing therefore returns false before ownership/configuration
   validation, and the private CLI exits 1.

A temporary local diagnostic exercised the actual serving-start lock
acquisition, production filesystem lifecycle inspection, runtime socket
borrowing, and proxy authorization. With identical installed, ownership, and
configuration fixtures, proxy authorization succeeded before acquisition,
failed while serving startup held the lock, and succeeded after release.
The serving probe deliberately ended after its lock and installed-state checks;
it did not simulate a complete systemd startup or live TLS serving. Unrelated
ownership/configuration/route reads used controlled valid fixtures.

Two other observations narrow the explanation:

- The exact retained ExecCondition text passes the production route parser;
  its `status=1` metadata does not itself make the route invalid.
- At `08:57:21Z–08:57:22Z`, invoking the installed authorization gate alone
  returned 0 without starting either service or changing ownership. The
  executable, ownership, and proxy configuration still matched the failure
  capture. The record was Running with no unfinished direction or client
  rotation, so this invocation did not consume a cutover authorization.

**Established:** the implementation rejects an otherwise valid proxy start
when it overlaps ordinary subscription startup's lock. **Inference:** this
race caused the observed live refusal. The simultaneous request, journal
ordering, later successful gate, and unchanged durable inputs support that
inference. No lock-owner trace or branch-specific error was recorded at
`07:47:48Z`, so exact historical attribution remains unproved.

Repair should address coordination between these two ordinary startup paths
while preserving mutation/removal/update exclusion and one-use cutover
authority. Removing the gate or treating every busy lock as safe would violate
those contracts. No such change was made here.

## Cleanup: certificate acceptance leaves an obsolete serving state file

The live Complete removal action refused at `07:52:50Z` with
`PROXY-INSTALLATION-ACTION-REFUSED`, failed check `Subscription absence`, before
committing removal. The persisted facts identify a concrete cause:

| Material | Fresh observation |
|---|---|
| Ownership Record | Accepted certificate generation 2; no pending repair, activation, or client rotation. |
| Four certificate files and canonical live links | Generation 2; hashes match the Ownership Record. |
| Subscription credential | Correct protected mode, canonical token format, matching credential digest. |
| `subscription-serving.json` | Still generation 1, with generation 1 certificate digests. Link identity and credential digest match current authority. |
| Serving state modification/change times | `07:09:34Z`, during URL rotation and before certificate replacement. |
| Supporting files | Expected directory modes/contents, empty staging, source-matching unit, recognized Certbot README, and no staged ownership or final-removal record. |

The generation mismatch is sufficient to refuse removal. The call chain is
Complete removal → `subscriptionRemovalSurfaceSafe` → `servingSurfaceSafe` →
[`InspectServingFiles`](../../../internal/proxyinstallation/adapter/host/serving.go).
That inspection requires the serving state bytes to equal
`servingStateBytes(currentAuthority)`. They do not. With no pending operation
authorizing an alternate state, the fallback also refuses, producing the
observed generic `Subscription absence` message.

The writer side explains the mismatch. Reviewed certificate replacement in
[`repair.go`](../../../internal/proxyinstallation/repair.go) activates the target,
checks published/loaded generation and HTTPS behavior, assigns
`record.Serving = record.Repair.Target`, and finishes its ownership checkpoints.
It never republishes `subscription-serving.json`. The related accepted
certificate path in [`activation.go`](../../../internal/proxyinstallation/activation.go)
likewise changes the Ownership Record without synchronizing that file.
The host's `ActivateServing` restarts and verifies the runtime; it does not
write serving state either.

This also explains how generation 2 passed the earlier live HTTPS checks.
Serving dispatch with renewal authority validates the selected certificate
from protected ownership and certificate material, and its sandbox omits the
ordinary state-file comparison. Published/loaded HTTPS checks do not compare
the stored serving state. The serving process can use generation 2 while a
later ownership-sensitive operation rejects the obsolete file.

The isolated reproduction exercised real files, modes, links, hashes, and the
production host inspector. Generation 2 files/links/authority with generation 1
state reproduced rejection. Changing only the disposable fixture's state to
generation 2 made that inspection pass. The same experiment reproduced and
cleared refusal in `ReadSubscriptionLink`, identifying another affected
consumer. It did **not** perform full removal or validate any live repair.

Existing replacement tests model certificate publication/activation in memory;
their host doubles do not carry this protected file through replacement and
subsequent removal. This is a missing integration check across certificate
acceptance, stored serving state, and later consumers.

Repair must maintain the accepted authority and protected serving state
consistently across replacement, activation, interruption, and finishing.
Regression coverage should continue through link retrieval and reviewed
removal using the real filesystem adapter. A manual state-file rewrite or
bypassing removal checks is not a validated repair and was not attempted.
