## Reproduced failure mechanism

The preflight executes:

```sh
go run ./cmd/sbxr-release verify-public-latest > current-source-verification.json
jq -e '.outcome == "accepted"' current-source-verification.json >/dev/null
```

The [CLI writer](../../../cmd/sbxr-release/main.go) successfully writes outcomes
`accepted`, `refused`, or `unavailable`; refusal/unavailability are result data,
not CLI execution errors. Either non-accepted outcome therefore makes the
following `jq` exit 1 with no displayed explanation.

A temporary test exercised real local HTTPS responses through the production
GitHub adapter, the actual `writePublicLatestVerification` function, and this
exact Bash/jq assertion:

| Supplied HTTPS response | CLI outcome | CLI writer | Shell assertion |
|---|---|---|---|
| 403 | `refused` | Success | Exit 1, empty stdout/stderr |
| 429 | `unavailable` | Success | Exit 1, empty stdout/stderr |
| 503 | `unavailable` | Success | Exit 1, empty stdout/stderr |

All three cases passed, as did the existing CLI outcome test. These deliberately
supplied responses prove the silent-failure mechanism; they do **not** establish
which response, if any, occurred in the original hosted runner. Other silent
assertions before declaration creation cannot be completely excluded from the
retained log alone.

The [production HTTP adapter](../../../internal/softwarelifecycle/adapter/github/github.go)
sets Accept, API-version, and User-Agent headers but does not use `GH_TOKEN`.
The workflow's authenticated `gh` operations and its public Go verifier therefore
have different HTTP authorization behavior. A rate-limit response, transient
network/service failure, or verification refusal remains a hypothesis; none is
confirmed for the failed run.

## Confirmed diagnostic gap and bounded follow-up

The workflow hides the existing safe outcome JSON and does not retain it on
early failure. The adapter also collapses HTTP/verification detail into broad
outcomes. Git history and ordinary tests cannot recover the dropped historical
runner response.

The smallest justified follow-up is to display a clear failure label with the
existing safe public-latest outcome and retain that JSON when preflight fails.
Keep the same refusal behavior and trust checks. If distinguishing transport
from trust failures is still necessary, capture only the specific sanitized
request stage/status or verification classification needed for that distinction.
No retry policy, timeout increase, new qualification gate, or new evidence
contract is justified by this investigation.

Exact reproduction on a GitHub-hosted runner remains unperformed. Another
candidate must not be used as the first diagnostic check.
