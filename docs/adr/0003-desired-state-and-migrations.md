# Desired State and migrations

SBXR keeps one typed, root-only JSON Desired State behind the State Module's `Load` and `PrepareCommit` Interface, while each owning Module inspects separate Observed State. Revision-bound one-use Plans, review-only sequential migrations, one transaction-scoped Rollback Snapshot, publication of Desired State last, automatic rollback of unfinished Change Sets, and **Recovery Required** on unprovable lineage were chosen over split files, in-place edits, silent migration, or best-effort recovery so stale or half-applied configuration can never become current Desired State; the canonical decisions are the [ticket 13 resolution](https://github.com/albertloky/SBXR/issues/13#issuecomment-5176418094) and [Decide the SBXR v1 recovery boundary](https://github.com/albertloky/SBXR/issues/21#issuecomment-5180278181).

Provider-created values have one explicit exception to pre-Apply completeness. The owning Module binds every fixed fact, exact empty provider-created slot, and evidence step in its one-use Plan. System Changes records each returned immutable identifier before any later provider step; secrets never enter that journal. State alone consumes the provider-issued secret, fills only those bound slots, recalculates the candidate, prepared-State, service-manifest, and transaction checksums, reruns all owning semantic validators, and replaces the protected prepared artifacts. System Changes durably records `Deferred State finalized` before activating prepared services or publishing State. A missing, changed, duplicate, contradictory, or unjournaled value stops publication and rolls back the Change Set; no Module may use this seam to change reviewed fixed facts or create another lock, journal, rollback store, or publisher.
