# Desired State and migrations

SBXR keeps one typed, root-only JSON Desired State behind the State Module's `Load` and `PrepareCommit` Interface, while each owning Module inspects separate Observed State. Revision-bound one-use Plans, review-only sequential migrations, one transaction-scoped Rollback Snapshot, publication of Desired State last, automatic rollback of unfinished Change Sets, and **Recovery Required** on unprovable lineage were chosen over split files, in-place edits, silent migration, or best-effort recovery so stale or half-applied configuration can never become current Desired State; the canonical decisions are the [ticket 13 resolution](https://github.com/albertloky/SBXR/issues/13#issuecomment-5176418094) and [Decide the SBXR v1 recovery boundary](https://github.com/albertloky/SBXR/issues/21#issuecomment-5180278181).

Provider-created values have one explicit exception to pre-Apply completeness. The owning Module binds every fixed fact, exact empty provider-created slot, and evidence step in its one-use Plan. System Changes records each returned immutable identifier before any later provider step; secrets never enter that journal. State alone consumes the provider-issued secret, fills only those bound slots, recalculates the candidate, prepared-State, service-manifest, and transaction checksums, reruns all owning semantic validators, and replaces the protected prepared artifacts. System Changes durably records `Deferred State finalized` before activating prepared services or publishing State. A missing, changed, duplicate, contradictory, or unjournaled value stops publication and rolls back the Change Set; no Module may use this seam to change reviewed fixed facts or create another lock, journal, rollback store, or publisher.

Tunnel run-token rotation has a narrower State-owned protected finalization exception after one additional irreversible checkpoint. Every owning semantic validator runs before Apply; the reviewed Plan and prepared candidate then bind the complete existing Tunnel, DNS, route, State, service, and non-token Cloudflare meaning while leaving only the replacement token deferred. System Changes records `Irreversible run-token rotation started`, removes the old token and its rollback copies, and pauses for the Owner to select **Rotate token** in Cloudflare. Recovery retrieves the current token through `GET /accounts/{account_id}/cfd_tunnel/{tunnel_id}/token`; State accepts only a changed opaque Infrastructure Secret into that one bound slot, reruns full structural and cross-section validation, rebuilds and checksums the protected candidate and service material, and publishes after cloudflared restarts and both routes pass. No other reviewed field can change during this finalization. Before the checkpoint, ordinary rollback applies. After it, every failure is forward-only Recovery Required and no path may restore or reconnect with the old token.

A deliberately removed Cloudflare management token is a typed State fact, not an empty or unreadable secret. Cloudflare Tunnel must first produce one reviewed replacement or removal Plan. For replacement, State alone consumes the already verified protected token and the old token remains current until publication. For removal, the Plan must either prove there are no dependent behaviors or list Tunnel, DNS, certificate, profile, repair, and update dependencies with the one reviewed result that marks all of them unmanaged. State then recalculates and validates the complete candidate before publication. System Changes keeps the old State as its Rollback Snapshot until `Complete`; no other Module may directly add, replace, clear, or infer this secret.
