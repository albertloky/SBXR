# Installation preflight and SSH safety

SBXR admits only a proven Clean VPS or current Managed installation through staged, revision-bound preflight; requires the Owner to start Installation from one direct active SSH session; owns one nftables table without fighting another firewall manager; treats the approved profile ports as defaults with safe random alternatives for occupied configurable ports; preserves the detected SSH port through atomic firewall application and automatic rollback without requiring a second SSH connection; keeps provider-firewall correction manual; and mutates only Cloudflare resources proven by immutable IDs under the minimum persisted account-and-zone authority. The complete Owner Console remains available without direct SSH for operations that cannot make a forward firewall change. The bootstrap validates an available direct SSH session identity once, carries it only through an explicit SBXR internal launch value, and requires fresh agreement with the active service, exact listener, and established connection before that value becomes SSH Preservation Proof. Only that original direct session is sufficient. Every Installation or Managed Client Access forward firewall mutation requires the same proof. SBXR rechecks it during preflight, immediately before the firewall change, and immediately after the firewall change before cancelling the rollback watchdog. It rolls back if the session disappears and never substitutes another session on the same port. An authorized rollback or armed watchdog can restore the reviewed prior firewall without SSH Preservation Proof and does not prove later SSH reconnection. The root-only unfinished Change Set stores the raw SSH connection identity. Restart recovery captures the new direct SSH session identity, appends it to the Change Set, and requires fresh SSH Preservation Proof before a new forward firewall mutation; saved identities have no authority without fresh live agreement. SBXR deletes every raw identity when the Change Set reaches Managed or rolls back and retains only required SHA-256 evidence. A VPS provider console can restore SSH but cannot supply SSH Preservation Proof required to start Installation. A missing or invalid launch identity and a closed original session require exit and restart from direct SSH; only a temporary service, listener, or socket observation failure offers Check again. One typed proof failure distinguishes those causes while each operation retains its existing stable public failure code. These choices favor bounded automatic rollback and exact Correction Flows over unsafe adoption, provider-specific credentials, indefinite retries, or bypass controls; the canonical decision is [Define installation preflight and SSH safety](https://github.com/albertloky/SBXR/issues/12#issuecomment-5187474911).
