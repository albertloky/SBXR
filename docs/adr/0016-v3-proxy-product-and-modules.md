# Establish the V3 proxy product and Modules

V3 is a new SBXR product line for one Owner and one Ubuntu Server 24.04 `amd64` host. It is not a migration from V1 or V2. This decision extends the original V3 boundary with the accepted subscription and sequential Client Identity replacement contract in [#342](https://github.com/albertloky/SBXR/issues/342), handed off by [#343](https://github.com/albertloky/SBXR/issues/343). It records implementation authority, not implementation or qualification success.

## Approved scope change: first subscription release uses clean installation

On 2026-09-01 Albert selected option 1: clean installation for the first subscription-capable release, with supported Update/Recover access in the existing numbered menu for future releases. This decision supersedes the conflicting first-source requirements in Implementation Decision 11, Testing Decisions, #335/#338, and #344–#357. All unrelated safety and evidence requirements remain normative.

The first subscription-capable release declares no supported incoming upgrade sources. In-place upgrade or migration from `v3.0.21` or any earlier release is unsupported. An existing Owner uses the old release's reviewed Complete removal, finishes any interrupted removal through its supported exact-release route, proves `Not installed`, then clean-installs the qualified new release and performs setup. This entails downtime, new proxy credentials and client setup. Preserve unrelated/shared resources. Do not run an installer over a remaining installation, copy protected state, preserve/relabel old credentials as a migration, or treat removal plus installation as a successful upgrade. This decision does not authorize removal of a live installation now.

The new release must expose Software Lifecycle `Check`, `Update`, and `Recover` through the same root-only, zero-argument numbered menu. Keep Proxy Installation's Review/Execute Interface and Action vocabulary unchanged; lifecycle choices call the existing Software Lifecycle Interface. Require explicit Owner confirmation before update/recovery effects, fresh admission checks, and the existing transaction authority. Do not add CLI subcommands, a second menu, helper executable, hidden mode, or an umbrella Module. A release without qualified incoming upgrade support is never an update target merely because its Release Sequence is newer.

The single Release Qualification gate must explicitly distinguish the first subscription clean-install scope from later recurring upgrades. Bind that scope, the exact candidate and verified current stable identity, an empty incoming source set, and the exact applicable scenario list into the signed attempt and Acceptance Record. Permit the exception only while no earlier subscription-capable Qualified Stable Release exists; unavailable or unproved release history refuses. Do not infer it from an empty source list or reuse historical first-V3 evidence to qualify subscription behavior. Revalidate this condition at stable publication; a changed baseline requires fresh qualification.

For this first release, actual incoming source upgrades and their two-release update/recovery scenarios are explicitly not applicable, not passed. Keep exhaustive automated lifecycle admission/rollback/runtime-recovery tests, packaged menu reachability and safe no-update/no-recovery/refusal behavior, clean installation, and every subscription, Client Identity, certificate, removal, secret-safety, SSH, outside-network, and final exact Karing obligation. Existing schema-1 conversion tests must use a state produced by the candidate's supported setup, not edited protected records or an unsupported migration. Required cases that cannot be reached safely remain missing evidence. #355 implements the lifecycle route and safety behavior; reopened #356 implements this strict scope distinction; #357 performs the applicable packaged/live proof.

Subsequent subscription releases must again declare and qualify the then-current subscription-capable stable source plus any other explicitly supported sources, using each source's own unchanged packaged updater and actual recovery contracts. Both releases must understand every Update Record they can encounter. The first clean-installed release becomes an eligible source only when that later real source-to-candidate path passes; its own publication does not prove future upgrade compatibility. No bridge release, patched old bytes, alternate migration route, or general evidence waiver is approved.

#344's negative package findings remain valid. Close it as superseded by this scope decision, not as a successful source-upgrade qualification. Stable publication and live host mutations still require their existing authorization and qualification gates.

## Module ownership and production entry

Proxy Installation owns legal actions, both derived statuses, Plans, Prepared Actions, Confirmation, the Whole-Host Mutation Lock policy, Ownership Record publication, proxy and subscription runtime lifecycle, credential and certificate lifecycle decisions, durable checkpoints, interruption direction, repair, recovery, progress/results, disclosure, and Complete removal. Software Lifecycle retains installed-software status, Installed Record and executable verification, Release Identity, qualified stable discovery, Release Sequence, Update Record direction, rollback, forward completion, recovery, and exact-executable restoration during unfinished Complete removal. Their private collaboration enforces compatible update admission and required subscription runtime completion; it creates no second recovery authority.

The standard-library numbered line menu remains presentation: proxy choices call Proxy Installation directly, and lifecycle Check/Update/Recover choices call the existing Software Lifecycle Interface. Proxy Installation's only public operations remain exactly `Review(context.Context, Action) Review` and `Execute(context.Context, PreparedAction, Confirmation, ProgressReporter) Result`. Review performs fresh inspection and required read-only preflight. A legal Review may create one opaque, memory-only, single-use Prepared Action. Execute consumes it once and revalidates the required facts under the mutation lock before effects; stale, reused, invalid, mismatched, or changed-fact authority refuses without mutation or disclosure. Read-only inspection never finishes pending work.

Add one concrete private Module at `internal/proxyinstallation/subscriptionserving`, without a Go interface for one implementation. `Prepare` builds validated immutable serving state from typed current Proxy Profile and generation facts. `Inspect` converts serving-state/runtime observations into secret-safe facts. `Serve` runs fixed HTTPS behavior from trusted active state and a bound listener, returning typed terminal outcomes. It owns artifact encoding, authentication, request limits, TLS loading, and network failure containment. It neither imports Proxy Installation nor owns durable authority, host mutation, legal actions, or recovery.

One private Host Adapter supplies Ubuntu filesystem, APT, identity, process, listener, network, Certbot, recorder, firewall, systemd, and exclusion mechanics. One private sing-box Adapter owns official key handling, configuration encoding/validation, typed current connection facts, and replacement of only the VLESS user credential. It must not use whole-identity generation to rotate REALITY keys or short ID. Both remain private Adapter seams with production and test Adapters, not Owner Interfaces.

Keep one root-only, zero-argument Owner entry point. Protected private systemd/hook/recorder/startup dispatch uses the same executable package, fixed validated roles, and proved installed/ownership/runtime authority. Serving dispatch calls Serve directly; activation retains Proxy Installation authority. An environment string or arbitrary command is not authorization. Missing or conflicting authority refuses and cannot be recreated by a caller. Add no CLI subcommand, second menu, umbrella Journey/coordinator, scheduler, hidden test mode, or alternate transaction harness. The approved lifecycle choices use the existing numbered menu.

## Status, Actions, and disclosure

Retain Actions `Status`, `View details`, `Start setup`, `Finish cleanup`, `Finish setup`, `Show client configuration`, `Complete removal`, and `Finish removal`. Add exactly:

| Action | Exact prompt |
|---|---|
| `Enable subscription` | `Enable subscription? [y/N]` |
| `Rotate subscription link` | `Rotate subscription link? [y/N]` |
| `Repair subscription` | `Repair subscription? [y/N]` |
| `Finish subscription change` | `Finish subscription change? [y/N]` |
| `Rotate Client Identity` | `Rotate Client Identity? [y/N]` |
| `Finish Client Identity rotation` | `Finish Client Identity rotation? [y/N]` |

Exact `y` approves; `n` or empty input declines; other input grants no authority. Declining consumes the Prepared Action and leaves earlier pending work unchanged. Preserve existing Complete removal and already-committed Finish removal confirmation behavior. No show-link, disable, subscription-only removal, or healthy renew-now action is added.

Show `Proxy status:` and `Subscription status:` separately on each menu frame. Proxy Installation Status is `Not set up`, `Running`, `Change in progress`, `Change incomplete`, `Setup incomplete`, `Removal incomplete`, or `Problem detected`. The added `Change incomplete` is only for interrupted Client Identity rotation with proved direction. Status does not prove traffic availability. Typed Review and Result data carry the separate Subscription Capability Status and secret-safe observations; availability facts distinguish `proved working`, `proved stopped`, and `cannot be verified` for proxy traffic and subscription serving. Unknown is never boolean success.

| Subscription Capability Status | Meaning and action gate |
|---|---|
| `Not enabled` | Absence of capability and unfinished subscription work is proved. A freshly verified Running proxy with safe idle authority may enable it. |
| `Available` | Fresh local credential, state, certificate, service/listener, and renewal checks pass, without a known subscription security problem. This is not public reachability or Karing proof. Link rotation requires safe replacement facts. |
| `Change in progress` | A subscription-affecting operation is observed active. No concurrent mutation is legal. |
| `Change incomplete` | Durable authority proves pending subscription work and its direction; among subscription mutations, only proved finishing is legal. |
| `Problem detected` | Failed check/renewal, compromise, unverifiable capability, or unknown/conflicting authority. Repair, rotation, both, or neither depend on the exact proved facts. |

Observed active work takes precedence over proved pending work, then fault; retain fault details. Unknown direction grants no finishing action. Pending Client Identity rotation directs affected subscription finishing to `Finish Client Identity rotation`; a proved absent subscription stays `Not enabled`. An independent subscription fault leaves a freshly proved healthy proxy `Running` without concealing a separate proxy fault.

Repair needs one diagnosed safe correction preserving the link, Proxy Profile, and Client Identity. Healthy capability, public-IP drift, and unresolved ownership conflict do not permit repair; public-IP drift also forbids link rotation. Link rotation requires agreement on the current generation and safe replacement facts. An unrelated outage alone neither allows nor forbids it. Known/suspected link leakage requires an immediate safe rotation attempt; failed preparation retains the old authority and visible security problem. Link rotation cannot revoke proxy credentials already copied from an artifact.

View details remains read-only in every state. During whole-host mutation, block concurrent mutations and Client Configuration disclosure. Pending setup, removal, update recovery, subscription work, or identity rotation blocks new identity rotation. Pending identity rotation also blocks Client Configuration disclosure; a subscription outage alone does not remove the independently verified, confirmed fallback. Active shared Certbot or managed writers cause bounded retry refusal, never termination or indefinite waiting.

Plans name the action, statuses/fault, exact owned effects, network requirements, interruption, credential effects, and proved recovery direction. Enablement includes dependencies, renewal, local proof limits, and possible shared-lineage delay from recorder-start failure. Link rotation names unchanged Client Identity and no overlap; identity rotation names old-session disconnection, unchanged link/other fields, actual availability, manual fallback, possible extended outage, and the leaked-link warning. Repair names one correction; finishing names remaining effects and direction. Update/removal warn about shared-renewal delay and extended outage if finishing fails.

Use dedicated optional secret-bearing `SubscriptionLink []byte` fields on Review for authorized View details redisclosure and Progress for completed enablement/rotation disclosure, including successful forward finishing. Exclude them from diagnostic serialization and ordinary formatting. Never place them in Details, Plan, Phase, Result messages, errors, or logs. Status Review never fills the field. View details discloses only after fresh agreement among credential file, digest, Link ID, serving state, and Ownership Record; a certificate/listener fault alone does not hide a consistent existing link, but remains visible beside it. Failed or unfinished changes never disclose a candidate. Client Configuration remains a separate confirmed disclosure, never an automatic rotation result.

Whenever the link is displayed, use exactly:

> This link is a reusable credential. Anyone with it can obtain your proxy connection details. Keep it private. It will remain in terminal scrollback.

After link rotation also use exactly:

> Replace the old link in Karing. The old link no longer works. Your proxy Client Identity has not changed.

Pause with the existing Enter-to-return pattern. The terminal tracks actual output separately from committed mutation. Failed output after commitment cannot undo it or repeat rotation; use the display-incomplete outcome and direct the Owner to View details where possible. Failed read-only disclosure exits unsuccessfully and cannot report successful disclosure or mutation. Rotation success does not claim Karing refreshed. If the revoked proxy blocks link refresh, explain temporary direct access through a working connection or the separately confirmed fallback; never silently change Karing settings.

Validate one immutable certificate/key generation, lineage, recorded address, trust, and validity before activation and on every start. At loaded NotAfter, stop TCP `8443`; never weaken TLS. Fresh public-IP drift stops serving and requires Complete removal and new setup/enablement, not automatic reissue or address migration. Independently healthy proxy traffic remains separate.

Renewal Attempt Evidence is a protected, bounded diagnostic record, never stored status, mutation authority, or a recovery journal. Durably record exact attempt/installation/invocation before permitting the scheduled child to launch; recorder-start failure blocks the child and may delay unrelated lineages. Missing completion is unknown outcome. Retain unresolved failures across no-op or unrelated successes; clear only after proved successful owned renewal plus activation, or reviewed correction establishing missing outcome and current safety. Refuse new managed invocation if safe bounded retention is impossible.

Only the recorder and validated outcome writers may publish that diagnostic evidence without the Whole-Host Mutation Lock. Serialize and bind evidence writes to the exact attempt/installation. Never hold their publication lock while waiting for the whole-host lock or child completion. All runtime effects and Ownership Record writes still require whole-host authority. Certbot canonical publication can occur outside that lock: compare published, accepted, and loaded generations. Standing exact-lineage authority can prove missed forward activation without a saved hook operation; Review observes it, confirmed Execute records it before effects. Merge only compatible certificate activation into pending authority, without a competing operation or changed credential target. No background repair or guaranteed hook replay is added.

Acquire whole-host authority, exclude new managed work, and prove writers/children idle before destructive or executable-replacement effects. Use bounded nonblocking admission and revalidation, the supported Certbot POSIX `lockf` protocol and lock-inode checks, never file existence or unrelated `flock`. Owner-driven Certbot retains the parent's whole-host authority; the parent validates/activates, with owned directory hooks suppressed by `--no-directory-hooks` after checking effective CLI/global/lineage hooks for unsupported re-entry. No child may reacquire a parent-held incompatible lock; no alternative directories or lock-inode replacement bypass exclusion. Exact safe lock/child plumbing still needs implementation and packaged proof.

## Durable authority, revocation, and startup

Ownership Record remains the only durable proxy/subscription authority. Strictly validate supported schema 1 and schema 2, safe files, unknown fields, internal consistency, and exact resource contracts; a schema number alone proves no compatibility. Schema 2 preserves proxy phase, original creating Release Identity, package/configuration identity, address, destination, and actual resource provenance. It adds subscription/recorder/startup provenance, accepted serving/certificate identities, Link ID/digest, standing exact-lineage renewal authority, and at most one unfinished subscription or Client Identity operation. Software update remains an Update Record transaction. Store no raw credential, artifact, or Infrastructure Secret in ownership.

Convert schema-1 Running authority only within confirmed Enable subscription or Rotate Client Identity, under the mutation lock before effects. Confirmed Complete removal may convert when committing removal. Inspection and ordinary updates never convert; failed enablement or cancelled rotation may retain valid schema 2 without downgrade. Already committed schema-1 removal keeps its original interpretation and exact-release binding.

Each operation binds independent operation ID, kind, source/target identities and prepared material, exact authorized effects, cleanup/forward direction, commitment, startup gate where applicable, and completed effects. Before every effect publish its authority and prove absence or matching created ownership; a planned path alone is not ownership. Each record, credential, configuration, state, and evidence publication separately requires expected-current checks, safe parents, protected staging, complete writes, file sync, atomic rename, and directory sync. Re-observe late failures and prove durability before dependent effects. Visible rename or staging alone cannot choose direction. Unknown direction reports `Problem detected`, with no guessed rollback, forward work, or deletion. Observe possibly completed effects before retry; verify staging cleanup before clearing authority.

| Operation | Before commitment | Commitment and forward rule |
|---|---|---|
| Enable subscription | Cleanup-directed preparation and provisional local verification; no candidate disclosure. | Commit only after local agreement, then retain the same generation, finish cleanup/bookkeeping, and disclose. |
| Rotate subscription link | Prepare one target with old link authoritative; record stop authority and prove no old process/accepted request can serve further responses. | Durably select target before canonical publication; never restore revoked link or regenerate target. Old path is concealed 404 when the replacement listener works; outage is not HTTP refusal. |
| Repair subscription | Prepare one diagnosed correction; cleanup removes unused preparation. | Save forward checkpoint before correction/restart; finish only that correction, not restoration of the fault. |
| Certificate activation | Certbot publication is separate from SBXR activation. | Valid owned publication plus standing authority proves forward activation; save target before runtime effects, never roll back Certbot history. |
| Rotate Client Identity | Prepare one replacement while canonical source remains unchanged; establish startup gate and prove old-session/old-artifact quiescence. | Only then durably select replacement as sole identity. Finish exact target; no post-revocation source restoration, even for availability. |

Client Identity rotation replaces only SBXR-generated VLESS UUID. Preserve address/port, destination, REALITY key pair/short ID, all other connection fields, node name, package/provenance, Subscription Link, credential, and Link ID. At most one Client Identity is authorized, without overlap or session grace period. A leaked link can fetch the replacement; warn to rotate that link first, never couple the actions silently.

Admission requires freshly verified Running proxy, compatible executable/records/resources, current configuration, and safe replacement/startup facts. Absent or independently unavailable subscription is admissible, but unknown/conflicting material is not absence. Proved absent startup integration may be installed by a supported owned route. Record integration publication, systemd reload, and effective-route verification separately. Establish a durable cutover gate across every supported ordinary start/restart/hook route before stopping services. Before the gate only unchanged source may start; afterward ordinary starts refuse until finishing completes. Direct official proxy startup must not bypass the gate.

Pause Subscription Serving, stop proxy traffic, and prove exact owned process groups and descendants cannot continue old sessions or emit further old-artifact responses, and listeners cannot accept new work. Stop exit status, process-name matching, or listener absence alone is insufficient. Already transmitted bytes and client caches cannot be erased. After durable revocation, publish only prepared target state and start via authorized finishing. If target cannot start, leave proxy stopped for forward finishing; unknown durability permits neither direction.

Pre-revocation finishing restores only proved unchanged source, removes unused target, and reports cancelled rotation with cleanup. A fully installed compatible startup integration may remain explicitly owned; incomplete preparation requires owned cleanup and effective-route verification. Known compromise remains a problem. Post-revocation finishing verifies target proxy, saved connection details, startup safeguards, and cleanup. A separate subscription availability fault can remain while verified target proxy runs; stale or uncertain artifact material blocks completion. Reopen ordinary starts only after required completion. Boot chooses no recovery direction and performs no issuance, repair, credential generation, or pending-action completion. Removal authority denies all owned starts/writers across death/reboot; missing authority never allows state recreation.

## Compatible update and Complete removal

Creating Release Identity is provenance, not a blanket equality requirement with the active executable. Preserve each resource's actual creator. Candidate compatibility must prove the actual ownership/package/resource, serving, recorder/evidence/hook, startup, and recovery contracts while preserving full Installed Record/executable verification. For recurring subscription releases, declare exact qualified active source Release Identities, including the then-current subscription-capable Qualified Stable Release; admit older sources only with actual packaged upgrade evidence. The approved first subscription clean-install scope declares no incoming sources and cannot be selected as an in-place update target. Unlisted/unknown sources refuse without an invented intermediate release.

Ordinary update preserves Ownership Record bytes and both credentials, with no conversion or resource migration in the rollback window. Refuse pending proxy/subscription/identity work, committed removal, unsafe compatibility, and active renewal/writers before replacement. Keep existing serving process through Committed subject to certificate validity; private routes cannot admit uncommitted candidate bytes as installed authority. Before Committed restore exact verified compatible prior executable/Installed Record and route. After Committed retain candidate and restart only enabled Subscription Serving; verify executable, selected generation, accepted state, certificate, service/listener, and cleanup before completion/reopening renewal. Preserve sing-box. Retain Update Record through failed runtime activation and observe completed effects rather than blindly restarting. Runtime completion/admission belongs in Software Lifecycle's supported Update Record contract, not a competing subscription operation. Historical records keep their meaning; both releases in the recovery path must understand a versioned expansion. Renewal evidence cannot select update direction or clear unrelated failures.

Complete removal may supersede proved idle unfinished enablement, link rotation, repair/activation, or identity rotation on either side of commitment without first repairing availability. Revalidate safe supported authoritative record, unchanged Prepared Action facts, compatible verified finishing executable, unambiguous direction/generation, complete provenance, and idle exclusion. Prove absence or exact ownership for every deletion. Expired certificate, public-IP drift, or safely missing resources alone do not block removal; unknown ordering/ownership does. Never start or disclose either generation to make removal possible.

At Removal committed separately bind the exact installed Finishing Release Identity, preserving all creating identities and current/source/target/provisional/startup/transaction inventory. Removal is forward-only, in this order:

1. Establish idle admission and Certbot/writer exclusion; commit full removal authority; stop Subscription Serving and prevent restart/reactivation; prove process/request/listener quiescence.
2. Under compatible exclusion remove only proved owned dedicated lineage, renewal configuration, certificate generations/keys/canonical links, and hooks. Preserve unrelated lineages and shared ACME account. No CA/network dependency.
3. Remove owned recorder integration, preserve current official generated service route and unrelated overrides, reload and verify the remaining route before allowing it to run. Never restore a stale whole service file or use broad `systemctl revert`.
4. Prove no owned entry point, child, hook, or evidence writer can recreate state; remove owned recorder/evidence, credentials/digests, serving/candidate/staging/transaction state, units/enablement links, startup integration, and exact firewall contributions, never broad port matches. Remove directories only when safely empty.
5. Finish existing proxy cleanup; remove created dependencies only with exact provenance and proof of no unrelated use, otherwise deliberately preserve them. Preserve reused packages/snaps, shared accounts, unrelated data/logs/configuration, SSH, routing, and provider settings.
6. Freshly prove complete owned absence and safe retained shared-renewal route. Remove executable/Installed Record through Software Lifecycle, then finalize Ownership Record last.

Unfinished shared-route restoration keeps its scheduled invocation blocked, including after reboot; Plans/details disclose possible delay to unrelated certificates. Once safe restoration is proved, unrelated renewal need not await remaining proxy cleanup. Keep strict final state-directory inspection: expanded stores must already be absent before executable deletion; unknown residue refuses, never recursive cleanup. Preserve complete schema-2 removal authority through `/var/lib/.sbxr-removal.json` with exactly one authoritative location. Exact restoration uses the removal-bound release, not Latest or assumed creator; legacy committed schema 1 keeps its existing release binding. Wrong bytes, unknown schema, contradictory records, or residue refuse. Restoration never reinstalls proxy resources or revives revoked credentials. `Not installed` requires fresh absence of executable, Installed Record, Ownership Record, and all proved V3-owned resources; `Not set up` leaves SBXR installed without proxy capability. No provider-firewall cleanup reminder is added.
