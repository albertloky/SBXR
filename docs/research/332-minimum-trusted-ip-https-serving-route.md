# Minimum trusted IP-HTTPS route for Karing Subscription Serving

Research snapshot: 2026-08-30. This note resolves planning research only. It does not design the final Module, implement Subscription Serving, or qualify a real VPS or Karing client.

## Question

On Ubuntu Server 24.04 `amd64`, what exact first-party constraints govern the minimum publicly trusted IP-address HTTPS Subscription Serving route on a fixed non-443 port, including ACME validation on TCP 80, six-day certificate renewal, certificate reload, Karing trust and refresh behavior, provider-firewall limits, secret-safe serving, and failure behavior?

## Answer

The smallest currently supported route is:

1. Keep sing-box on public TCP `443`.
2. Serve the Subscription Link with an SBXR-owned Go `net/http` service on one separate fixed TCP port.
3. Obtain one publicly trusted certificate for the recorded public IPv4 address with official Certbot `5.4` or later, the Let's Encrypt `shortlived` profile, the `--ip-address` identifier, and the Certbot `standalone` authenticator.
4. Keep public TCP `80` reachable for every issuance and renewal. Certbot binds TCP `80` only while it answers HTTP-01, so no permanent second web server is needed.
5. Let Certbot's scheduled renewal check renew the 160-hour certificate. Run one SBXR-owned deploy hook only after successful renewal to restart the Subscription Serving service so Go loads the new `fullchain.pem` and `privkey.pem`.
6. On renewal failure, leave the last successfully loaded certificate and the proxy service untouched, report Subscription Serving as unhealthy, and retry through the owned renewal mechanism. Never fall back to plain HTTP or disabled certificate verification.

This route requires an official Certbot snap rather than Ubuntu 24.04's `apt` package: Ubuntu Noble publishes Certbot `2.9.0`, while IP-address support arrived in Certbot `5.3` and Let's Encrypt requires `5.4` or later for its documented webroot route. The current official Certbot snap is `5.7.0`, supports `amd64`, and includes automatic renewal. The exact snap revision, command behavior, timer, hook access, and Ubuntu compatibility remain packaged VPS acceptance facts, not static proof.

Karing's visible source accepts an `https` profile URL without rejecting a literal IP or explicit non-443 port. Its official docs support remote Profile Links, VLESS, and refresh. However, the public repository omits the actual fetch and auto-conversion implementation. Static research therefore cannot prove that Karing validates a literal-IP SAN correctly, accepts SBXR's eventual payload, preserves a last-known-good profile after an update failure, or carries traffic. Those are mandatory live Karing acceptance gates.

## Verified first-party facts

### Public IP certificates and validation

- Let's Encrypt made IPv4 and IPv6 address certificates generally available in January 2026. They use the `shortlived` profile, are valid for 160 hours, and permit IP identifiers. [Let's Encrypt general-availability announcement](https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability.html) [Let's Encrypt profile table](https://letsencrypt.org/docs/profiles/#shortlived)
- IP-address certificates must use the short-lived profile. Let's Encrypt's current Certbot instructions require Certbot `5.4` or later for webroot IP support and use `--preferred-profile shortlived` with `--ip-address`. Certbot obtains the certificate but does not install it into the server; the server must load `/etc/letsencrypt/live/<ip address>/fullchain.pem` and `privkey.pem`. [Let's Encrypt Certbot instructions](https://letsencrypt.org/2026/03/11/shorter-certs-certbot)
- HTTP-01 can validate an IP address and always connects to TCP `80`. Let's Encrypt may fetch the challenge several times from several network vantage points. Redirects do not move validation to an arbitrary port: only HTTP or HTTPS redirects to TCP `80` or `443` are accepted. [Let's Encrypt challenge documentation](https://letsencrypt.org/docs/challenge-types/#http-01-challenge)
- TLS-ALPN-01 always uses TCP `443`. SBXR's current Proxy Profile already owns the public TCP `443` listener, so using TLS-ALPN-01 would collide with sing-box or require a new TCP-443 multiplexer. HTTP-01 on TCP `80` is the smaller independent route. [Let's Encrypt challenge documentation](https://letsencrypt.org/docs/challenge-types/#tls-alpn-01) [SBXR V3 endpoint preflight at `989094b`](https://github.com/albertloky/SBXR/blob/989094b9766f02bf17510a71753c6a5c736bf120/internal/proxyinstallation/proxyinstallation.go#L1360-L1378)
- Certbot currently supports IP certificates through the `webroot`, `manual`, and `standalone` authenticators. Standalone runs its own temporary server and requires TCP `80` to be locally available and publicly reachable. Unlike webroot, it needs no continuously running HTTP server. [Let's Encrypt Certbot instructions](https://letsencrypt.org/2026/03/11/shorter-certs-certbot) [Certbot standalone documentation](https://eff-certbot.readthedocs.io/en/stable/using.html#standalone)

### Ubuntu and Certbot packaging

- Ubuntu Server 24.04's Noble repository publishes Certbot `2.9.0-1`. That version predates both `--preferred-profile` in Certbot `4.0` and `--ip-address` in Certbot `5.3`, so the Ubuntu `apt` package cannot implement this route. [Ubuntu Noble package](https://packages.ubuntu.com/noble/certbot) [Let's Encrypt Certbot version requirements](https://letsencrypt.org/2026/03/11/shorter-certs-certbot)
- Certbot's official installation documentation recommends the snap for modern systemd Linux distributions. It supports `x86_64`, includes automatic certificate renewal, and avoids stale LTS distribution packages. The official Snap Store published Certbot `5.7.0` as `latest/stable` on 2026-07-21. [Certbot installation documentation](https://eff-certbot.readthedocs.io/en/stable/install.html#snap-recommended) [Official Certbot snap](https://snapcraft.io/certbot)
- The official snap is installed with classic confinement. That is a high-authority dependency, not a sandboxed helper. SBXR must inventory whether `snapd` and the `certbot` snap already exist, verify the installed Certbot version is at least `5.4`, record what it owns, and remove only what it proved it created. [Official Certbot installation instructions](https://certbot.eff.org/instructions)

### Renewal and certificate reload

- Certbot `renew` reuses the authenticator and options from issuance. For certificates valid for ten days or less, Certbot considers renewal due when less than half the lifetime remains. For a 160-hour certificate, the default threshold is therefore about 80 hours before expiry. The command may run frequently because it does nothing when renewal is not due. [Certbot renewal documentation](https://eff-certbot.readthedocs.io/en/stable/using.html#renewing-certificates)
- Most Certbot installations include scheduled renewal; the official snap expressly includes it. A deploy hook runs only after a successful issuance or renewal and receives `RENEWED_LINEAGE`, which points to the new live certificate directory. `certbot renew` returns zero both when renewal succeeds and when nothing was due, so a deploy hook, not command exit alone, is the correct reload trigger. [Certbot renewal hooks](https://eff-certbot.readthedocs.io/en/stable/using.html#renewing-certificates) [Certbot snap installation](https://eff-certbot.readthedocs.io/en/stable/install.html#snap-recommended)
- Certbot updates `/etc/letsencrypt/live/<certificate-name>` to the latest certificate files. Its documentation says servers should point directly to these files rather than copy them. [Certbot certificate storage](https://eff-certbot.readthedocs.io/en/stable/using.html#where-are-my-certificates)
- Go's `http.Server.ListenAndServeTLS` loads the certificate and key when the server starts unless the program supplies a dynamic `tls.Config.GetCertificate` or `GetConfigForClient`. Restarting the one Subscription Serving service after a successful deploy hook is therefore the minimum reload mechanism; an in-process certificate watcher or signal protocol is not required. [Go `net/http` server documentation](https://pkg.go.dev/net/http#Server.ListenAndServeTLS) [Go `net/http` TLS setup source](https://go.dev/src/net/http/server.go)
- Go checks an IP URL against the certificate's IP-address Subject Alternative Name, not its Common Name. A port is not part of certificate identity. Therefore `https://<public-ip>:<fixed-port>/...` can use a certificate for `<public-ip>` even though the port is not `443`. [Go `crypto/x509.VerifyHostname`](https://pkg.go.dev/crypto/x509#Certificate.VerifyHostname)

### Why the existing Go ACME dependency is not the minimum issuance route

- SBXR currently targets Go `1.26.6` and already carries `golang.org/x/crypto v0.54.0` indirectly. [SBXR `go.mod` at `989094b`](https://github.com/albertloky/SBXR/blob/989094b9766f02bf17510a71753c6a5c736bf120/go.mod)
- At `v0.54.0`, `acme/autocert` creates a DNS-name CSR and calls `acme.DomainIDs`; its exported order options can set only `notBefore` and `notAfter`, not an ACME profile. It therefore does not expose the required IP-identifier plus `shortlived` order as a supported `autocert` route. Reimplementing ACME profile and IP-order handling inside SBXR would be larger and less proven than using current official Certbot. [Go `autocert` at `v0.54.0`](https://github.com/golang/crypto/blob/v0.54.0/acme/autocert/autocert.go#L653-L697) [Go ACME order options at `v0.54.0`](https://github.com/golang/crypto/blob/v0.54.0/acme/types.go#L378-L395)

### Karing URL, trust, and refresh behavior

- Karing's official Add Profiles documentation says a remote Profile Link supports sing-box, V2Ray, Shadowsocks, Clash/Stash, `sub`, and GitHub formats. Imported local files cannot update. Its FAQ lists VLESS as a supported protocol. [Karing Add Profiles documentation at `9a6b1b2`](https://github.com/KaringX/karing-docu/blob/9a6b1b248ea08e67682b28a31fbc02e211333cca/i18n/en/docusaurus-plugin-content-docs/current/app-manual/add-profiles.md#L15-L30) [Karing supported protocols at `9a6b1b2`](https://github.com/KaringX/karing-docu/blob/9a6b1b248ea08e67682b28a31fbc02e211333cca/i18n/en/docusaurus-plugin-content-docs/current/faq.md#L22-L28)
- Karing `v1.2.24+2707` sends a pasted Profile Link to its remote auto-conversion path. The visible validation accepts `http` or `https` by scheme and does not reject literal IP hosts or explicit ports. An official source comment gives a nested HTTPS subscription URL on port `8443`. This proves the visible URL layer accepts the intended shape, not that the omitted fetcher completes it. [Karing add-link flow at `fbaf360`](https://github.com/KaringX/karing/blob/fbaf3600e9239db14882d594907879230004921f/lib/screens/add_profile_by_link_or_content_screen.dart#L241-L276) [Karing URL validation at `fbaf360`](https://github.com/KaringX/karing/blob/fbaf3600e9239db14882d594907879230004921f/lib/screens/my_profiles_edit_screen.dart#L274-L286) [Karing port-8443 example at `fbaf360`](https://github.com/KaringX/karing/blob/fbaf3600e9239db14882d594907879230004921f/lib/screens/scheme_handler.dart#L22-L31)
- New Karing remote profiles default to a 12-hour update interval. The user can disable or change it, with five minutes as the minimum non-null interval. Karing checks due profiles on VPN connect, application resume, after initialization, and periodically on desktop; the interval makes a profile eligible and is not an exact fetch deadline. [Karing remote-profile default at `fbaf360`](https://github.com/KaringX/karing/blob/fbaf3600e9239db14882d594907879230004921f/lib/screens/add_profile_by_link_or_content_screen.dart#L56-L76) [Karing interval validation at `fbaf360`](https://github.com/KaringX/karing/blob/fbaf3600e9239db14882d594907879230004921f/lib/screens/add_profile_by_link_or_content_screen.dart#L631-L650) [Karing refresh scheduling at `fbaf360`](https://github.com/KaringX/karing/blob/fbaf3600e9239db14882d594907879230004921f/lib/app/modules/server_manager.dart#L464-L497)
- Karing documents `CERTIFICATE_VERIFY_FAILED` as a real failure and directs the user to restore current system roots. It does not document a trust-all fallback. [Karing certificate error at `9a6b1b2`](https://github.com/KaringX/karing-docu/blob/9a6b1b248ea08e67682b28a31fbc02e211333cca/i18n/en/docusaurus-plugin-content-docs/current/faq.md#L284-L285)
- The current public Karing tree imports fetch and auto-conversion helpers that are not present in that tree. Static source cannot prove exact payload grammar, redirects, HTTP headers, response limits, TLS hostname matching, or last-known-good behavior after refresh failure. Those facts require live acceptance against the selected packaged Karing build. ### Network and provider-firewall constraints

- The ACME server must reach the recorded public IPv4 on TCP `80` during every issuance and renewal. The Karing device must reach the same public IPv4 on the selected Subscription Serving port. A successful local bind proves neither path. [Let's Encrypt HTTP-01 documentation](https://letsencrypt.org/docs/challenge-types/#http-01-challenge)
- SBXR currently states that it does not change the host firewall or provider settings. A blocked provider firewall is therefore a manual Correction Flow unless a later decision explicitly changes that ownership boundary. [Current SBXR setup plan at `989094b`](https://github.com/albertloky/SBXR/blob/989094b9766f02bf17510a71753c6a5c736bf120/internal/proxyinstallation/proxyinstallation.go#L1368-L1378)
- The VPS needs one stable, directly reachable public IPv4. Carrier-grade NAT, provider port forwarding to another address, a changed public IP, or blocked inbound TCP `80` invalidates this route. These are consequences of validating and later connecting to the exact IP identifier; no static repository check proves them.

### Secret-safe serving constraints

- A token carried inside a pasted URL is a bearer credential: possession is sufficient to use it. The OAuth bearer-token RFC warns that URI-carried bearer tokens are likely to be logged and prefers an Authorization header. Karing's visible pasted-link Interface does not expose a separate Authorization-header field, so any URL token is an explicit product compromise that the artifact-contract ticket must own. [RFC 6750 bearer-token definition and URI warning](https://www.rfc-editor.org/rfc/rfc6750.html#section-2.3)
- HTTPS protects the URL from passive network disclosure after TLS is established, but it does not prevent disclosure from Owner copy/paste history, Karing storage, screenshots, process arguments, application logs, server access logs, support bundles, or retained acceptance output. This is an inference from bearer-URL semantics.
- Go's standard HTTP server does not add access logging by itself. The minimum server can expose only the exact authenticated GET route and a non-secret local health path, omit request-target logging, reject every other method and path, bound response size, use fixed response headers, and return no directory listing or diagnostic body. These are design implications, not behavior supplied automatically by `net/http`.
- The response contains the Client Identity even when the URL token is separate. It must use `Cache-Control: no-store`, must never be retained in Acceptance Records or logs, and must be compared and disclosed only through the eventual deep Module's secret rules. The exact token format, path shape, rate limit, rotation, and status codes remain for later decision tickets.
- Certbot account material and the certificate private key are Infrastructure Secrets. The Subscription Serving process needs read access to the active private key; unrelated local users do not. The eventual design must settle service identity and file ownership rather than weakening `/etc/letsencrypt` permissions.

## Planning implications

1. Use official Certbot `5.4+` from the official snap and reject Ubuntu Noble's Certbot `2.9.0`. Bind qualification to an observed version and supported command behavior; do not assume the drifting `latest/stable` revision is unchanged.
2. Use standalone HTTP-01. It is smaller than a permanent TCP-80 webroot service and does not interrupt sing-box or the non-443 Subscription Serving listener during validation.
3. Reserve public TCP `80` for temporary Certbot validation and one fixed non-443 TCP port for Subscription Serving. Refuse setup before mutation if either local bind is unavailable. Treat provider-firewall reachability as a separate outside fact and Correction Flow.
4. Run only a successful-renewal deploy hook, and restart only Subscription Serving. Do not restart sing-box. Do not build dynamic certificate reload unless measured interruption makes the simple restart unacceptable.
5. Make certificate health independent from proxy traffic health. Failed renewal or expired TLS must not stop, reconfigure, or downgrade the Running Proxy Profile.
6. Fail closed: no self-signed production fallback, `InsecureSkipVerify`, plain HTTP Subscription Link, stale-address acceptance, or serving after the certificate or private key becomes unreadable or mismatched.
7. Treat Certbot, its snap, ACME account, lineage, private key, renewal task, hook, Subscription Serving service, listener, token, and artifact as owned resources only when SBXR recorded that it created them. Preserve pre-existing shared resources.
8. The later deep-module decision must own issuance checkpoints, renewal observation, recovery, repair, rotation interaction, and Complete removal. Certbot's automatic timer is mechanism, not SBXR's durable authority.

## Required packaged VPS and Karing acceptance

Static research does not satisfy any item below:

1. On a fresh Ubuntu Server 24.04 `amd64` Acceptance VPS, inventory pre-existing `snapd`, Certbot, TCP `80`, the selected service port, firewall state, and provider-firewall rules.
2. Install through the selected production path; prove the exact Certbot version is at least `5.4`, the snap provenance is official, its scheduled renewal is active, and its hook can restart only the intended systemd service.
3. From a genuinely outside network, prove public TCP `80` reaches Certbot during staging HTTP-01. Then obtain a production certificate and prove its chain is publicly trusted, its IP SAN exactly matches the recorded public IPv4, and its validity is 160 hours.
4. Prove the fixed non-443 HTTPS endpoint works with normal certificate verification from outside. Prove the wrong IP, an untrusted chain, an expired certificate fixture, and a mismatched certificate fail closed.
5. Paste `https://<public-ip>:<fixed-port>/<token>` into the selected packaged Karing build. Prove initial fetch, exact eventual payload import, REALITY field preservation, outside traffic through the VPS, and manual plus scheduled refresh of the unchanged URL.
6. Prove unauthorized, missing, malformed, empty, and oversized requests disclose no Client Identity. Prove retained logs, journal, GitHub output, Acceptance Record, screenshots, and cleanup evidence contain neither the URL token nor subscription body, UUID, REALITY private key, certificate private key, or raw public address.
7. Force one successful staging renewal and prove the deploy hook loads the new certificate without changing or interrupting sing-box beyond the accepted boundary. Force CA/network, blocked-TCP-80, hook, and service-restart failures; prove the old certificate remains active while valid, the failure becomes visible, recovery is deterministic, and the proxy remains Running.
8. Change the observed public IPv4 and prove stale-address serving and renewal fail closed with a safe Correction Flow.
9. Exercise interruption at every durable setup, issuance, activation, renewal, hook, repair, and removal checkpoint selected by the later design.
10. Complete removal must delete every proved SBXR-owned subscription, certificate, account, hook, timer/service, port, and package artifact while preserving all pre-existing snap, Certbot, certificate, firewall, systemd, and unrelated host resources. Outside HTTPS and Karing refresh must fail after removal while SSH and unrelated host behavior remain intact.
