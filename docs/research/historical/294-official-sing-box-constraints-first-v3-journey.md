# Official sing-box constraints for the first V3 journey

Research snapshot: 2026-08-24. The current stable first-party release checked here is `v1.13.19`, published on 2026-08-17. This note supports planning only. It does not implement V3 or qualify a live journey.

## Question

What current first-party installation, package-signing, configuration-validation, systemd, VLESS REALITY, and official outside-client requirements constrain the smallest safe Ubuntu Server 24.04 amd64 to VLESS REALITY to official sing-box outside-client traffic to owned-resource removal journey?

## Verified source facts

### Installation and package trust

- The official Debian/APT instructions install the stable package named `sing-box`. They download `https://sing-box.app/gpg.key` to `/etc/apt/keyrings/sagernet.asc`, make it readable, configure `https://deb.sagernet.org/`, and bind that repository to this key with `Signed-By: /etc/apt/keyrings/sagernet.asc` before `apt-get update` and `apt-get install sing-box`. [Official package-manager documentation](https://sing-box.sagernet.org/installation/package-manager/)
- The live official repository publishes a clear-signed `InRelease` for the literal `*` suite and `*` component. Its `amd64` package index currently contains `sing-box` `1.13.19`, identifies SagerNet as vendor, and publishes SHA-256 `fb628b8cedf3e4c7cb32aa9c5103e0457e65ebb35ef510d041118836ef3b33bf` for the DEB. [Official signed repository metadata](https://deb.sagernet.org/dists/*/InRelease) [Official amd64 package index](https://deb.sagernet.org/dists/*/*/binary-amd64/Packages)
- The matching first-party release publishes `sing-box_1.13.19_linux_amd64.deb`. Its control metadata says `Architecture: amd64` and declares no package dependencies. It installs `/usr/bin/sing-box`, `/etc/sing-box/config.json`, `sing-box.service`, `sing-box@.service`, and the `sing-box` system-user definition. [Official v1.13.19 release](https://github.com/SagerNet/sing-box/releases/tag/v1.13.19) [Package build inputs at v1.13.19](https://github.com/SagerNet/sing-box/tree/v1.13.19/release/config)
- The shipped `/etc/sing-box/config.json` is a live example that listens on `::` TCP port `8080` with a fixed Shadowsocks password. The package installs it as root-owned mode `0644`. The DEB's only `postinst` action creates the `sing-box` system user; the package does not enable or start the service and contains no `prerm` or `postrm` cleanup script. [Tagged vendor configuration](https://github.com/SagerNet/sing-box/blob/v1.13.19/release/config/config.json) [Tagged post-install script](https://github.com/SagerNet/sing-box/blob/v1.13.19/release/config/sing-box.postinst) [Official v1.13.19 amd64 DEB](https://github.com/SagerNet/sing-box/releases/download/v1.13.19/sing-box_1.13.19_linux_amd64.deb)
- The official instructions publish the key URL but do not publish an independent expected fingerprint on that page. Trust bootstrap therefore depends on fetching the documented key from the first-party HTTPS endpoint; this research did not find a second first-party fingerprint channel. [Official package-manager documentation](https://sing-box.sagernet.org/installation/package-manager/) [Official key](https://sing-box.app/gpg.key)
- The first-party docs label third-party builds that change the official build tags as problematic. Official Linux builds include the `with_utls` tag required by the REALITY client implementation. [Problematic-sources warning](https://sing-box.sagernet.org/installation/package-manager/#problematic-sources) [Official v1.13.19 default build tags](https://github.com/SagerNet/sing-box/blob/v1.13.19/release/DEFAULT_BUILD_TAGS)

The official docs describe Debian/APT installation, and the official release supplies an `amd64` DEB. They do not state a named Ubuntu 24.04 support guarantee. Actual Ubuntu Server 24.04 amd64 compatibility remains a live qualification item.

### Configuration validation

- sing-box configuration is JSON. The documented validator is `sing-box check`; the global `-c/--config`, `-C/--config-directory`, and `-D/--directory` flags select the same inputs and working directory used by `run`. With no `-c` or `-C`, the binary defaults to `config.json`. [Official configuration documentation](https://sing-box.sagernet.org/configuration/) [v1.13.19 command flags](https://github.com/SagerNet/sing-box/blob/v1.13.19/cmd/sing-box/cmd.go) [v1.13.19 validator](https://github.com/SagerNet/sing-box/blob/v1.13.19/cmd/sing-box/cmd_check.go)
- `check` does more than JSON parsing: it reads and merges the selected configuration, constructs a sing-box instance, and then closes it. This catches configuration decoding and instance-construction errors, but it does not start listeners or prove outside traffic. [v1.13.19 validator](https://github.com/SagerNet/sing-box/blob/v1.13.19/cmd/sing-box/cmd_check.go) [v1.13.19 configuration loading](https://github.com/SagerNet/sing-box/blob/v1.13.19/cmd/sing-box/cmd_run.go)
- To validate the packaged service's exact inputs, the matching command is `sing-box -D /var/lib/sing-box -C /etc/sing-box check`. A check of some other file or working directory is not proof for the unit. [v1.13.19 systemd unit](https://github.com/SagerNet/sing-box/blob/v1.13.19/release/config/sing-box.service)

### systemd behavior

- The packaged unit runs as user `sing-box`, uses systemd `StateDirectory=sing-box`, and starts `/usr/bin/sing-box -D /var/lib/sing-box -C /etc/sing-box run`. It grants a bounded set of ambient capabilities, including `CAP_NET_BIND_SERVICE`, `CAP_NET_ADMIN`, and `CAP_NET_RAW`; restarts on failure after 10 seconds; and is only enabled when an operator requests it. [v1.13.19 systemd unit](https://github.com/SagerNet/sing-box/blob/v1.13.19/release/config/sing-box.service) [Official service-management commands](https://sing-box.sagernet.org/installation/package-manager/#service-management)
- `systemctl reload sing-box` sends `SIGHUP`. On `SIGHUP`, sing-box first runs its own `check`; if validation fails, it logs the reload error and keeps the existing instance. If validation succeeds, it closes the old instance and creates a new one from the configuration. [v1.13.19 systemd unit](https://github.com/SagerNet/sing-box/blob/v1.13.19/release/config/sing-box.service) [v1.13.19 reload loop](https://github.com/SagerNet/sing-box/blob/v1.13.19/cmd/sing-box/cmd_run.go)
- A restart is not the same safety boundary as reload. An invalid configuration makes a fresh `run` exit; `Restart=on-failure` then retries it after 10 seconds. The official log command is `journalctl -u sing-box --output cat -e` (or `-f` for new logs). [v1.13.19 run path](https://github.com/SagerNet/sing-box/blob/v1.13.19/cmd/sing-box/cmd_run.go) [Official service-management commands](https://sing-box.sagernet.org/installation/package-manager/#service-management)

### VLESS REALITY server and client

- A VLESS inbound requires at least its `users` field by schema, and each user requires a UUID. The only documented VLESS `flow` value is `xtls-rprx-vision`. [Official VLESS inbound documentation](https://sing-box.sagernet.org/configuration/inbound/vless/)
- A VLESS outbound requires `server`, `server_port`, and `uuid`. `network` can be `tcp` or `udp`, and both are enabled by default. The only documented `flow` value is `xtls-rprx-vision`; XUDP is the default UDP packet encoding. [Official VLESS outbound documentation](https://sing-box.sagernet.org/configuration/outbound/vless/)
- Server REALITY requires a handshake destination and a private key generated by `sing-box generate reality-keypair`. Client REALITY requires the paired public key. `short_id` is required by the docs and is described there as a hexadecimal string from zero through eight digits. The server can optionally enforce `max_time_difference`; an empty value disables that time check. [Official REALITY fields](https://sing-box.sagernet.org/configuration/shared/tls/#reality-fields)
- The v1.13.19 client implementation rejects REALITY unless `tls.utls.enabled` is true. It requires a 32-byte decoded public key and accepts a decodable short ID of at most eight bytes. The docs' eight-digit limit, their 16-digit example, and the implementation's eight-byte limit do not agree. An eight-hex-digit non-empty value is inside all three observed bounds. The official build enables `with_utls`. [Official REALITY structure and fields](https://sing-box.sagernet.org/configuration/shared/tls/#reality-fields) [v1.13.19 REALITY client](https://github.com/SagerNet/sing-box/blob/v1.13.19/common/tls/reality_client.go) [v1.13.19 default build tags](https://github.com/SagerNet/sing-box/blob/v1.13.19/release/DEFAULT_BUILD_TAGS)
- The v1.13.19 server accepts the configured TLS `server_name` and forwards unauthenticated handshakes to the configured REALITY handshake destination. The outside client must therefore carry the matching `server_name`, paired public key, matching short ID, and VLESS UUID. This matching requirement is an inference from the first-party server and client implementation, not a single normative sentence in the docs. [v1.13.19 REALITY server](https://github.com/SagerNet/sing-box/blob/v1.13.19/common/tls/reality_server.go) [v1.13.19 uTLS client](https://github.com/SagerNet/sing-box/blob/v1.13.19/common/tls/utls_client.go)
- REALITY conflicts with ECH in the v1.13.19 implementation. The server also rejects ACME certificate configuration, ordinary certificate/key configuration, and curve preferences when REALITY is selected. The first journey does not need an owned domain or certificate. [v1.13.19 REALITY server](https://github.com/SagerNet/sing-box/blob/v1.13.19/common/tls/reality_server.go) [v1.13.19 uTLS client](https://github.com/SagerNet/sing-box/blob/v1.13.19/common/tls/utls_client.go)

### Official outside-client traffic

- The official sing-box binary supports client operation by combining a local inbound with a proxy outbound. A `mixed` inbound is one local server that accepts SOCKS4, SOCKS4a, SOCKS5, and HTTP proxy traffic. This is smaller than TUN or graphical-client setup for the first TCP traffic proof. [Official client model](https://sing-box.sagernet.org/manual/proxy/client/) [Official mixed inbound](https://sing-box.sagernet.org/configuration/inbound/mixed/)
- A local mixed listener needs an explicit `listen` address; `listen_port` selects its port. Leaving `users` empty means the local proxy has no authentication, so a safe journey must bind it to loopback rather than an outside interface. [Official listen fields](https://sing-box.sagernet.org/configuration/shared/listen/) [Official mixed inbound](https://sing-box.sagernet.org/configuration/inbound/mixed/)
- System-proxy operation only covers applications that honor HTTP proxy settings and only TCP. A traffic proof through an explicitly configured local SOCKS/HTTP client is therefore narrower and clearer than claiming device-wide coverage. TUN is the official route for broader TCP and UDP capture, but it is not required for this first journey. [Official client manual](https://sing-box.sagernet.org/manual/proxy/client/)

## Planning implications and inferences

1. Use the official signed APT path and the stable package, not the pipe-to-shell installer or a third-party build. Record the installed version and package provenance. A deterministic journey should decide whether to pin the version or accept repository drift; that is a planning decision, not a source fact.
2. Treat package trust bootstrap as a named security boundary. The current official procedure has one HTTPS-delivered key and no independently documented fingerprint. Do not claim independent key verification.
3. Never start the packaged vendor configuration. Install the package while the unit remains disabled and stopped; atomically replace the vendor file with the V3 configuration; set a mode such as `root:sing-box 0640` so the service can read the REALITY private key but unrelated local users cannot; validate; then enable/start. The exact owner and mode are a security-planning inference, not an upstream prescription.
4. Before changing a running service, validate the exact packaged input set with `sing-box -D /var/lib/sing-box -C /etc/sing-box check`, then reload. Preserve the current configuration until the reload succeeds. Do not use restart as the first validation attempt.
5. Keep the first server configuration small: one VLESS inbound, one generated UUID, `xtls-rprx-vision`, REALITY enabled, one generated keypair, one eight-hex-digit short ID, one explicit TLS `server_name`, and one reachable TLS handshake destination. Do not add ACME, certificates, ECH, multiplex, TUN, subscriptions, or graphical-client behavior to prove this journey.
6. Use an official `v1.13.19` sing-box binary or package on a genuinely outside machine. Its client configuration needs a loopback-only mixed inbound and a VLESS outbound with the server address/port, UUID, `xtls-rprx-vision`, TLS, matching `server_name`, `utls.enabled`, paired REALITY public key, and matching short ID. Validate that configuration with that exact client binary before starting it.
7. Prove traffic with a named TCP request explicitly sent through the local mixed proxy. Record the destination response and independent observed egress IP. This proves one outside TCP path; it does not prove all device traffic, UDP, a graphical client, or a subscription import.
8. Removal must be ownership-aware and cannot rely on an upstream removal script because the DEB contains none. Remove only the configuration, state, package, system user/group, APT source, and APT key that the journey can prove it created. If sing-box, `/etc/sing-box`, `/var/lib/sing-box`, `/etc/apt/sources.list.d/sagernet.sources`, `/etc/apt/keyrings/sagernet.asc`, or the `sing-box` identity existed before the journey, they are not automatically SBXR-owned.

## Open and live-acceptance items

- Confirm the exact `sing-box` version offered to a fresh Ubuntu Server 24.04 amd64 VPS at journey time, and preserve `apt-cache policy sing-box`, installed package metadata, and repository signature success as evidence.
- Confirm the official DEB installs and the packaged unit starts on the selected Ubuntu Server 24.04 amd64 image. The first-party sources do not promise that exact OS release by name.
- Select and live-check a REALITY handshake destination that is reachable from the VPS, speaks compatible TLS on the selected port, and accepts the chosen `server_name`. This is environmental behavior, not something static documentation can prove.
- Confirm VPS firewall, provider firewall, and routing allow the chosen inbound TCP port without changing SSH access.
- Run the client from a genuinely outside network. Prove the request fails or has a different egress path without the proxy, succeeds through the local mixed listener, exits from the VPS, and reaches the named destination.
- Exercise invalid-config reload behavior and successful reload behavior on the packaged unit. Static source inspection does not replace that live proof.
- Inventory pre-existing resources before installation, then verify removal deletes every journey-owned resource and preserves every pre-existing resource. Confirm the service is absent/inactive, the port is closed, the outside client can no longer pass traffic, and SSH still works.
- Maintained graphical-client qualification, device-wide traffic, UDP traffic, subscription import, stable release promotion, and any V3 implementation remain out of scope for this research ticket.
