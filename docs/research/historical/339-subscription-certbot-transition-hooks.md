# Official Certbot evidence for Subscription Serving transitions

Research snapshot: 2026-08-31. This note supports [Design crash-safe Subscription Serving transitions](https://github.com/albertloky/SBXR/issues/339). It records source facts and design constraints; it does not approve product policy, implement hooks, run Certbot, or qualify a VPS.

The inspected release is Certbot `v5.7.0`, whose annotated tag resolves to commit `e75e7378cd024d74d18a22c66d5aea32abd474c7`. All source links below pin that commit. The relevant hooks, renewal, locking, identifier, and snap files also match the inspected `main` commit `2b817be14620d65f5215460e0022b1a7eb6eefd1`. The installed snap version has not been inspected. [Official release](https://github.com/certbot/certbot/releases/tag/v5.7.0)

## Verified facts

### Scheduling and locks

- The snap declares a oneshot `renew` app with command `bin/python3 -s $SNAP/bin/certbot -q renew` and timer `00:00~24:00/2`. Its comment describes approximately twice-daily randomized runs. This supports retaining the official scheduled renewal without adding an SBXR renewal timer. [Official snap definition](https://github.com/certbot/certbot/blob/e75e7378cd024d74d18a22c66d5aea32abd474c7/snap/snapcraft.yaml#L42-L49)
- Certbot locks its work, logs, and config directories. Those locks coordinate Certbot instances, not unrelated processes. They are not the SBXR Whole-Host Mutation Lock. [Official lock documentation](https://eff-certbot.readthedocs.io/en/stable/using.html#lock-files)
- On Unix, Certbot acquires its lock with `fcntl.lockf(fd, fcntl.LOCK_EX | fcntl.LOCK_NB)` and raises `LockError` for a conflicting lock. SBXR must treat Certbot lock contention as an unsuccessful attempt, not bypass it using separate directories. [Official Unix locking implementation](https://github.com/certbot/certbot/blob/e75e7378cd024d74d18a22c66d5aea32abd474c7/certbot/src/certbot/_internal/lock.py#L120-L131)

### Hooks and publication

- Renewal saves the successor and updates the live symlinks before calling the deploy hook. Therefore a hook cannot acquire the SBXR lock before that Certbot publication. [Official renewal ordering](https://github.com/certbot/certbot/blob/e75e7378cd024d74d18a22c66d5aea32abd474c7/certbot/src/certbot/_internal/renewal.py#L549-L575)
- New issuance calls its deploy hook after enrollment. The common acquisition path runs a pre-hook and invokes post-hooks in `finally`. Explicit `certonly` uses that acquisition path. [Official acquisition path](https://github.com/certbot/certbot/blob/e75e7378cd024d74d18a22c66d5aea32abd474c7/certbot/src/certbot/_internal/main.py#L89-L148)
- Directory hooks have applied beyond `renew` since Certbot 3.2.0. A failing pre-hook does not stop renewal, so it cannot enforce an SBXR lock gate. `--no-directory-hooks` disables discovery of directory hooks; it does not disable hooks supplied through command arguments or configuration. [Official hook documentation](https://eff-certbot.readthedocs.io/en/stable/using.html#renewing-certificates)
- Hook collection first includes directory hooks when enabled, then the configured hook. A configured path still runs when directory hooks are disabled. Deploy-hook exit status is reported but not raised as a renewal failure. Dry runs omit deployment unless `--run-deploy-hooks` is enabled. [Official hook dispatch and execution](https://github.com/certbot/certbot/blob/e75e7378cd024d74d18a22c66d5aea32abd474c7/certbot/src/certbot/_internal/hooks.py#L192-L262)
- `renew` only enters acquisition when the lineage is due (or force/dry-run conditions apply). Post-hooks are collected from that acquisition path and run afterward. If no lineage is due, the next scheduled invocation does not replay a failed deployment or post-hook. A different due lineage can cause directory post-hooks to run, but that is not a retry guarantee. [Official due branch and saved post-hooks](https://github.com/certbot/certbot/blob/e75e7378cd024d74d18a22c66d5aea32abd474c7/certbot/src/certbot/_internal/renewal.py#L684-L748)

### Hook inputs are signals, not acceptance proof

- Deploy hooks receive `RENEWED_LINEAGE` and a space-separated `RENEWED_DOMAINS`. Renewal post-hooks receive accumulated `RENEWED_DOMAINS` and `FAILED_DOMAINS`; they do not receive a separately assigned per-lineage path. A post-hook must not infer its target from a possibly inherited `RENEWED_LINEAGE`. These identifier lists have size limits. [Official hook environment handling](https://github.com/certbot/certbot/blob/e75e7378cd024d74d18a22c66d5aea32abd474c7/certbot/src/certbot/_internal/hooks.py#L101-L245)
- The source builds these lists from certificate SAN objects, including IP addresses despite the `DOMAINS` suffix. IP strings are produced by Python's `ipaddress` representation. Parse identifiers as data; validate the exact expected lineage and certificate IP SAN rather than treating a string match as certificate acceptance. [Official IP identifier representation](https://github.com/certbot/certbot/blob/e75e7378cd024d74d18a22c66d5aea32abd474c7/certbot/src/certbot/_internal/san.py#L54-L83)

## Bounded orchestration supported by these facts

These are engineering inferences for the decision discussion, not accepted policy.

1. **Scheduled renewal:** let the official snap publish its Certbot lineage. The SBXR deploy entry point then attempts the Whole-Host Mutation Lock without waiting. Under that lock it re-observes the exact lineage, validates the replacement, records the required durable activation state, and uses the existing Subscription Serving activation path. Lock failure must not report successful activation.
2. **Owner repair:** the SBXR parent owns the Whole-Host Mutation Lock, records its repair intent, and invokes Certbot for the exact owned lineage. If the SBXR hooks are directory-only and there are no configured hooks that re-enter SBXR, `--no-directory-hooks` prevents a child hook from trying to acquire the parent's lock. The parent then validates and activates the result itself. Inspect the effective CLI/global/lineage configuration before relying on this; the flag alone is insufficient. Do not add an unchecked environment-variable bypass for lock ownership.
3. **External publication:** the Certbot lineage and the currently accepted serving certificate are separate facts. A locked SBXR operation cannot assume the lineage stayed unchanged merely because it holds the SBXR lock. It must bind validation and activation to the exact observed certificate/key generation and detect a changed or inconsistent observation.
4. **Interrupted activation:** a nonzero hook exit or successful `certbot renew` exit is not durable proof of SBXR activation. Inspection/recovery needs to detect a published-versus-accepted generation mismatch even if Certbot published and died before the hook ran or the hook could not acquire the lock. Do not mutate the pending SBXR transaction outside its lock merely to record hook contention.
5. **Retry limit:** retaining the snap schedule does not by itself guarantee timely deployment retry. A post-hook can give a second opportunity during a run that attempted renewal, but does not close the no-due-certificate gap. Owner completion, an already established reconciliation trigger, or a new explicitly approved mechanism must close that gap; this research does not choose one.

## Still unproved

- The actual snap version, enabled timer, effective hook configuration, filesystem ownership, and process environment on the target VPS.
- Crash behavior at each SBXR durable boundary and the consistency of certificate/key reads during external Certbot publication.
- Actual contention between scheduled renewal and Owner repair, bounded process completion, parent death, hook refusal, and absence of child re-lock deadlock.
- That a valid replacement reaches the live Subscription Serving listener while an invalid replacement leaves the valid loaded certificate undisturbed.
- Reliable discovery and correction of publication that occurred before a hook ran, failed, or obtained the SBXR lock.

These require implementation-level fault checks and exact packaged-executable/VPS acceptance. Official source inspection alone does not prove them.


## Follow-up: can native journal history account for every renewal attempt?

Research snapshot: 2026-08-31. Official systemd documentation source is pinned to commit `91927a2a1281be60f931e90d78e851d8ffd0688f`. This is an upstream source snapshot, not a claim about the VPS systemd version. Some convenience commands below are version-dependent.

### Source facts

- `_SYSTEMD_INVOCATION_ID` identifies the runtime cycle of the unit that emitted a message. `INVOCATION_ID` and `USER_INVOCATION_ID` instead identify the relevant unit cycle on messages produced by systemd code, including its manager. A reader must account for both forms and validate the trusted origin, unit, and boot fields. User-supplied fields without a leading underscore are not automatically trusted just because their name looks official. [Official field definitions](https://github.com/systemd/systemd/blob/91927a2a1281be60f931e90d78e851d8ffd0688f/man/systemd.journal-fields.xml#L103-L133) [Unit-cycle field](https://github.com/systemd/systemd/blob/91927a2a1281be60f931e90d78e851d8ffd0688f/man/systemd.journal-fields.xml#L307-L318)
- `journalctl --list-invocations` lists IDs and first/last message timestamps found in journal history. It is not a separate persistent execution ledger. `--verify` checks internal journal-file consistency and, when configured, authenticity; it does not establish that every service event was emitted and stored. `--sync` waits for journal synchronization, but cannot reconstruct a message never received. [Official invocation listing](https://github.com/systemd/systemd/blob/91927a2a1281be60f931e90d78e851d8ffd0688f/man/journalctl.xml#L923-L935) [Verify and sync](https://github.com/systemd/systemd/blob/91927a2a1281be60f931e90d78e851d8ffd0688f/man/journalctl.xml#L990-L1011)
- Cursors are opaque positions. Seeking to an unavailable cursor can succeed at the closest available entry. `sd_journal_test_cursor()` checks whether the actual anchor entry was found. That detects a missing anchor, not completeness of all later events. Do not parse a cursor into a supposed service-attempt counter. [Official cursor semantics](https://github.com/systemd/systemd/blob/91927a2a1281be60f931e90d78e851d8ffd0688f/man/sd_journal_get_cursor.xml#L46-L73)
- Journal storage can be volatile or disabled. Even persistent mode falls back to runtime storage during early boot or when disk storage is unavailable. Retention limits remove archived files. Rate limiting drops messages; severity filters can exclude them. Normal-priority records are synchronized on an interval, documented here as five minutes. These are explicit loss paths, not an append-only transaction log contract. [Official storage configuration](https://github.com/systemd/systemd/blob/91927a2a1281be60f931e90d78e851d8ffd0688f/man/journald.conf.xml#L75-L111) [Rate limits](https://github.com/systemd/systemd/blob/91927a2a1281be60f931e90d78e851d8ffd0688f/man/journald.conf.xml#L169-L190) [Synchronization](https://github.com/systemd/systemd/blob/91927a2a1281be60f931e90d78e851d8ffd0688f/man/journald.conf.xml#L366-L375) [Severity filters](https://github.com/systemd/systemd/blob/91927a2a1281be60f931e90d78e851d8ffd0688f/man/journald.conf.xml#L440-L458)
- The native journal send API explicitly returns success without writing anything when journald is not running and its socket is absent. Successful emission of a typed hook diagnostic is therefore not a durable outcome acknowledgement. [Official send return contract](https://github.com/systemd/systemd/blob/91927a2a1281be60f931e90d78e851d8ffd0688f/man/sd_journal_print.xml#L227-L238)

### Consequence for the proposed journal anchor

**Not sufficient as an authoritative completeness proof.** An accepted boot/invocation/cursor anchor plus matching later start/exit and hook messages can corroborate the runs that are present. Missing anchors, missing expected outcomes for visible invocations, unreadable history, and observed loss warnings can all justify `Problem detected`. However, absence of those warnings does not prove completeness: an entire later attempt can have no stored messages, while the earlier anchor remains readable. Invocation IDs are random identities, not contiguous attempt numbers. Current service result or last invocation cannot reconstruct an earlier hidden attempt.

This is a limit of the proposed evidence source. A reader cannot distinguish “no attempt happened” from “an attempt happened but all its messages were omitted” using that same journal alone. A fresh current configuration check cannot prove what the journal configuration and storage availability were throughout the interval. Declaring every unprovable interval `Problem detected` is safe but does not make this a usable positive-health test without an additional authority for completeness.

Secret-safe typed hook diagnostics remain useful for support and correlation, including lock contention. They should remain non-authoritative diagnostics and must not bypass the Whole-Host Mutation Lock to rewrite the Ownership Record.

### Minimal alternative if complete attempt accounting is required

A narrow **pre-execution durable attempt marker** can preserve the official timer schedule but requires an explicit change to the scheduled service path: a wrapper, or service integration with equivalent ordering, records the attempt durably before it can invoke Certbot. Failure to save the marker prevents that Certbot execution. Incomplete attempts remain visible after process death or reboot; later success must not silently overwrite an unresolved earlier attempt. Certificate publication and activation outcomes are then correlated with that marker, not inferred from log absence.

Systemd documents that a failing `ExecStartPre=` without a leading `-` prevents `ExecStart=`. This supports a strict marker-before-execution gate, unlike Certbot's nonfatal pre-hook. It does not itself supply the marker's durable storage or recovery protocol. [Official service command ordering](https://github.com/systemd/systemd/blob/91927a2a1281be60f931e90d78e851d8ffd0688f/man/systemd.service.xml#L426-L459)

This alternative adds no second renewal timer, but **does modify how the official scheduled service executes**, so it is outside a requirement to leave both timer and service unchanged. It also needs an explicit lock/ownership design for marker writes, interruption handling, refusal before the wrapper starts, protection against unaccounted direct Certbot invocations, and verification that snap refresh preserves the integration. None of those are proved here. If the required policy forbids such integration and any independent observer, full historical attempt accounting remains unsupported; use current certificate/serving observations and clearly bounded diagnostic evidence instead.


For the recorder variant under discussion, the receipt store could be explicitly separate from the Ownership Record and action authority, with its own bounded writer protocol. That would permit diagnostic receipt writes without claiming the SBXR mutation lock, but is an architectural choice that still needs approval. It must have durable identity and ordering, preserve unresolved attempts, refuse Certbot execution if the start receipt cannot be saved, and treat a missing terminal receipt as unknown even when the child may have succeeded. A shared official `renew` invocation processes multiple lineages: failure to save its start receipt would block renewal for unrelated lineages too. This host-wide consequence must be disclosed. Death before a successful start receipt prevents the child from being launched; death after that receipt leaves an observable incomplete attempt. Exact wrapper versus systemd command integration, process ownership, signal forwarding, terminal-result capture, and snap-refresh persistence remain specification/acceptance work, not decisions made by this note.
