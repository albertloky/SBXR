# Certificate Lifecycle

Certificate Lifecycle owns two fixed certificate lineages:

- `sbxr-ip` certifies only the selected subscription IP with the required `shortlived` profile.
- `sbxr-domain` certifies only the committed Direct TLS Hostname with the required `tlsserver` profile.

`View` reports both lineages, active serving identifiers, validity and due facts, Certbot capability, scheduler status, HTTP-01 prerequisites, exact DNS agreement, effective CAA, and secret-safe health. `Plan` binds one reviewed Owner email, explicit subscriber-agreement approval, the current State revision, fresh observations, and four typed order contracts with staging before production. The Ubuntu Adapter alone converts those contracts to the fixed command shapes, so Plans contain no raw command arguments.

The `sbxr-ip` Apply branch is one ordinary System Changes transaction. Certificate Lifecycle accepts only the typed HTTP-01 contribution produced by a fresh healthy Network Policy result; it cannot invent or relabel a firewall step. The transaction opens that one selected-address `tcp dport 80` rule, runs isolated staging, orders only the selected IP, validates the candidate, atomically switches the Subscription Serving pair, reloads or restarts only `sbxr-subscription.service`, and removes the recorded port-80 rule. Xray and its REALITY listener are not transaction steps. System Changes owns the global lock, durable snapshots, interruption handling, rollback, restart recovery, State publication, and the final cleanup decision.

The Owner-approved standing renewal policy admits only a valid due `sbxr-ip` or `sbxr-domain` branch. The IP certificate is due at 72 hours remaining and warns below 24 hours. The domain certificate follows a valid ACME Renewal Information suggested-window start; only an explicitly unavailable result uses the 15-day fallback, while malformed information fails closed. Either lineage retries an ordinary failure after 6 hours while its prior certificate remains valid and retries a busy global lock at the next bounded timer evaluation. The logical certificate identifiers, serving-pointer paths, and consumer bindings remain fixed in Desired State; a successful renewal publishes the next revision only after the Adapter has switched the protected pointer to the newly validated serving set.

The oneshot scheduler persists only each lineage's previous attempt time and the typed value `failed` or `busy` in separate root-owned `0600` files under `/var/lib/sbxr/certificate-renewal`. A later process reloads only that narrow fact; success removes only the completed lineage's file. Malformed, unsafe, symlinked, unavailable, or unknown history fails closed. The records contain no Owner email, ACME data, certificate material, command, raw output, journal content, or secret-derived value.

Exactly one `sbxr-cert-renew.service` and one `sbxr-cert-renew.timer` own renewal scheduling. Each evaluation checks IP then domain. Each due lineage obtains the System Changes lock separately, rebuilds a fresh one-use Plan only after the lock is held, and finishes before the next lineage starts. The persistent randomized calendar runs at least twice daily, while the same timer's bounded inactive interval permits the urgent busy retry window. Certbot-owned renewal timers and separate lineage timers are not part of SBXR.

The separate `sbxr-domain` Apply branch repeats that exact HTTP-01 boundary in its own Change Set. It orders only the committed Direct TLS Hostname, validates the complete `tlsserver` candidate, validates the complete sing-box configuration before mutation, atomically switches `/var/lib/sbxr/certificates/domain/current`, and restarts only `sing-box.service`. Hysteria2, TUIC, and AnyTLS then have separate Required checks using the selected VPS address as the destination and the committed hostname as the normally verified TLS name. Connection Profiles derives one short-lived `0600` probe from the exact active configuration and runs bounded native `sing-box tools connect` checks for the enabled outbounds; it refuses a changed address, hostname, port, type, or credential. The certificate Adapter never receives their credentials. REALITY, Cloudflare profiles, Subscription Serving, Xray, and diagnostics do not receive the domain pair.

Candidate validation uses the Go standard library to prove a complete trusted chain, matching private key, exactly one selected IP SAN, current validity, server authentication usage, and a 150-to-170-hour lifetime. Candidate directories and files must be root-owned regular non-symlink material at `0700` and `0600`. Active versioned Subscription Serving sets are `root:root 0755`; their chain and key are `0644`. Activation uses one relative `current` pointer and the fixed `sbxr-subscription.service`. A failed Required check restores that pointer, reloads or restarts the same unit, and re-proves the prior HTTPS endpoint without modifying or reordering the Certbot lineage.

Domain validation applies the same file, chain, key, trust, validity, and server-usage checks, but requires exactly one DNS SAN matching the committed hostname and a 40-to-50-day lifetime. Its active versioned serving set is `root:root 0755`; its chain and key are `0644`. Required configuration, restart, or individual consumer failure restores the prior shared pointer, restarts sing-box, and lets System Changes re-prove the complete prior service state. Rollback never rewrites `sbxr-domain`, never orders again, and deletes the rejected serving copy only after it is safe to do so.

The production Ubuntu Adapter accepts the recommended Snap package, including the official `/usr/local/bin/certbot` → `/snap/bin/certbot` symlink, and Certbot's supported pip alternative only inside a proved Python virtual environment. It requires version `5.4` or newer and checks for `--required-profile`, `--ip-address`, `--staging`, and the three isolation-directory flags. It reads each active public certificate through the validated root-owned serving pointer and makes bounded HTTPS GET requests to Let's Encrypt's production ACME directory and same-origin Renewal Information endpoint. The certificate identifier is the RFC 9773 base64url authority-key identifier plus DER serial-number content; response size, time, status, origin, JSON shape, and window order are checked without exposing response bodies. A directory or endpoint that explicitly cannot supply information selects the typed unavailable fallback; missing, malformed, cross-origin, or contradictory facts remain invalid. Ubuntu Server 24.04 Certbot `2.9.0`, `--preferred-profile`, another unproved distribution, malformed output, and missing capability fail closed.

Effective CAA may be empty or may authorize `letsencrypt.org` without a method restriction or with `validationmethods=http-01`. Another issuer, another method only, a critical unknown property, `SERVFAIL`, timeout, unavailable, or contradictory facts stop in `CERTIFICATE-CAA`. SBXR never changes CAA. Because HTTP-01 does not use `_acme-challenge`, unrelated CNAME, NS, and TXT records there are reported only as ignored facts.

Staging uses separate disposable account and lineage identities plus separate config, work, and log directories under `/var/lib/sbxr/certbot/staging`, `/run/sbxr/certbot`, and `/var/log/sbxr/certbot`. Staging cannot change the production configuration directory or ordinary trust stores.

Certificate Lifecycle owns the managed certificate input guidance. It validates one exact Owner email, explains that Let's Encrypt ended expiration notification emails on June 4, 2025, and marks the address as Personal Information supplied to the ACME client. Before exact `AGREE`, it supplies the current `https://letsencrypt.org/repository/` source and states that Help does not accept the agreement, authorize issuance, or approve a Plan.
