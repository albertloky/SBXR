# Certificate Lifecycle

Certificate Lifecycle owns two fixed certificate lineages:

- `sbxr-ip` certifies only the selected subscription IP with the required `shortlived` profile.
- `sbxr-domain` certifies only the committed Direct TLS Hostname with the required `tlsserver` profile.

`View` reports both lineages, active serving identifiers, validity and due facts, Certbot capability, scheduler status, HTTP-01 prerequisites, exact DNS agreement, effective CAA, and secret-safe health. `Plan` binds one reviewed Owner email, explicit subscriber-agreement approval, the current State revision, fresh observations, and four typed order contracts with staging before production. The Ubuntu Adapter alone converts those contracts to the fixed command shapes, so Plans contain no raw command arguments.

The `sbxr-ip` Apply branch is one ordinary System Changes transaction. Certificate Lifecycle accepts only the typed HTTP-01 contribution produced by a fresh healthy Network Policy result; it cannot invent or relabel a firewall step. The transaction opens that one selected-address `tcp dport 80` rule, runs isolated staging, orders only the selected IP, validates the candidate, atomically switches the Subscription Serving pair, reloads or restarts only `sbxr-subscription.service`, and removes the recorded port-80 rule. Xray and its REALITY listener are not transaction steps. System Changes owns the global lock, durable snapshots, interruption handling, rollback, restart recovery, State publication, and the final cleanup decision.

The separate `sbxr-domain` Apply branch repeats that exact HTTP-01 boundary in its own Change Set. It orders only the committed Direct TLS Hostname, validates the complete `tlsserver` candidate, validates the complete sing-box configuration before mutation, atomically switches `/var/lib/sbxr/certificates/domain/current`, and restarts only `sing-box.service`. Hysteria2, TUIC, and AnyTLS then have separate Required checks using the selected VPS address as the destination and the committed hostname as the normally verified TLS name. Connection Profiles owns a root-only `0600` probe configuration and runs bounded native `sing-box tools connect` checks for the three fixed outbounds; it refuses `insecure`, a custom trust anchor, a changed address, hostname, port, type, tag, or pointer. The certificate Adapter never receives their credentials. REALITY, Cloudflare profiles, Subscription Serving, Xray, and diagnostics do not receive the domain pair.

Candidate validation uses the Go standard library to prove a complete trusted chain, matching private key, exactly one selected IP SAN, current validity, server authentication usage, and a 150-to-170-hour lifetime. Candidate directories and files must be root-owned regular non-symlink material at `0700` and `0600`. Versioned Subscription Serving sets are `0750`; their chain and key are `0640` and shared only with the `sbxr-subscription` group. Activation uses one relative `current` pointer and the fixed `sbxr-subscription.service`. A failed Required check restores that pointer, reloads or restarts the same unit, and re-proves the prior HTTPS endpoint without modifying or reordering the Certbot lineage.

Domain validation applies the same file, chain, key, trust, validity, and server-usage checks, but requires exactly one DNS SAN matching the committed hostname and a 40-to-50-day lifetime. Its versioned serving set is `0750` and root-owned by the `sing-box` group; its chain and key are `0640`. Required configuration, restart, or individual consumer failure restores the prior shared pointer, restarts sing-box, and lets System Changes re-prove the complete prior service state. Rollback never rewrites `sbxr-domain`, never orders again, and deletes the rejected serving copy only after it is safe to do so.

The production Ubuntu Adapter accepts the recommended Snap package, including the official `/usr/local/bin/certbot` → `/snap/bin/certbot` symlink, and Certbot's supported pip alternative only inside a proved Python virtual environment. It requires version `5.4` or newer and checks for `--required-profile`, `--ip-address`, `--staging`, and the three isolation-directory flags. Ubuntu Server 24.04 Certbot `2.9.0`, `--preferred-profile`, another unproved distribution, malformed output, and missing capability fail closed.

Effective CAA may be empty or may authorize `letsencrypt.org` without a method restriction or with `validationmethods=http-01`. Another issuer, another method only, a critical unknown property, `SERVFAIL`, timeout, unavailable, or contradictory facts stop in `CERTIFICATE-CAA`. SBXR never changes CAA. Because HTTP-01 does not use `_acme-challenge`, unrelated CNAME, NS, and TXT records there are reported only as ignored facts.

Staging uses separate disposable account and lineage identities plus separate config, work, and log directories under `/var/lib/sbxr/certbot/staging`, `/run/sbxr/certbot`, and `/var/log/sbxr/certbot`. Staging cannot change the production configuration directory or ordinary trust stores.
