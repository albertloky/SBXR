# Software Lifecycle

Software Lifecycle owns SBXR release identity and delivery. One selected immutable tag either becomes one typed `VerifiedRelease` and one completely staged architecture payload, or `View` returns `SOFTWARE-LIFECYCLE-RELEASE-REFUSED` with no candidate or permitted mutation.

The genuine external Seam is `ReleaseSource`. The GitHub Adapter:

1. requires `/usr/bin/gh` version `2.97.0`, matches it to the installed `gh` Debian package, proves that package is unchanged, proves the configured APT origin is `https://cli.github.com/packages`, requires the reviewed current signing fingerprint `7F38BBB59D064DBCB3D84D725612B36462313325` in the configured keyring, and matches `/usr/bin/gh` to the exact immutable verified official `amd64` or `arm64` package bytes;
2. runs `gh release verify <tag> --repo albertloky/SBXR --format json`;
3. downloads each attested file from that same explicit tag through bounded standard output, stopping before more than 1 MiB for `release-index.json` or 256 MiB for any archive can enter memory or disk;
4. runs `gh release verify-asset <tag> <file>` for `release-index.json` and every downloaded payload; and
5. returns only the repository, tag, commit, asset digests, downloaded bytes, and verifier proof needed by `View`.

Raw verifier output and errors never cross the Adapter. `View` requires the attested, indexed, verified, and downloaded sets to agree exactly. The v1 index accepts only its ten named top-level fields and the four named fields for each of exactly four roles: two application archives and two matching offline component archives. Version and tag remain safe opaque strings; sequence, not version parsing, controls ordering. It rejects duplicate JSON keys, unknown fields, missing or duplicate roles/names, unsafe names, source ZIPs, malformed values, non-positive or oversized files, digest/size disagreement, extra or missing files, application archives that do not contain exactly one regular executable named `sbxr` with mode `0755`, unsafe or incomplete component manifests, and trailing gzip members.

`View` reports only installation status, installed identity when valid, verified and staged candidate proof, migration schema summary, eligibility, the four affected release assets, and currently permitted review action. It does not publish or execute an archive, change product State or the host, retain release history, expose Owner-managed values, accept ordinary HTTPS/checksums/earlier proof, or add an offline verifier.

Issue #128 adds one update-discovery path to that same `View`. The default asks GitHub only for the current stable release. Drafts and unintended prereleases are ignored; an alternate tag must be explicitly reviewed and cannot silently cross to another tag. `View` verifies the selected release through the existing exact five-file GitHub proof, accepts only a different Release Identity with a higher authenticated sequence, a compatible updater/index schema, and either the installed State schema or one complete sequential no-network forward migration path embedded identically in both application archives. It then offers only `Review update`. It never stages, extracts, executes, migrates, applies, or approves a discovered candidate.

Outside a transaction, the Ubuntu Adapter stores at most one newest verified unapplied candidate in `/var/lib/sbxr/software-lifecycle/update-candidate.tar`. A lock on the verified directory makes the sequence comparison and atomic replacement one operation, so overlapping checks cannot leave an older candidate. Replacement changes one root-owned `0600` file beneath a root-owned `0700` directory whose complete parent chain is non-linked, correctly owned, and not group/world-writable; an interrupted `.next` file is discarded on restart. The retained evidence is bounded and reverified byte-for-byte before `View` reports it. An older discovery cannot replace it, and there is no previous-release list or history browser.

Issue #126 lets `View` authenticate one selected architecture before the Ubuntu staging Adapter opens it in a fresh private directory. The Adapter never executes the candidate. It checks archive size, digest, entry type, ownership and mode, Linux ELF architecture, static linkage, Go `1.26.5`, `GOOS=linux`, selected `GOARCH`, and `CGO_ENABLED=0`, then removes the temporary copy.

The executable embeds repository, immutable tag, commit SHA, and the SHA-256 of its unstamped ELF bytes as its independent payload identity. Software Lifecycle binds those facts to the already authenticated external index and asset proof; the index SHA-256 remains outside the executable to avoid a circular archive digest. `sbxr version` reports the embedded facts. A later installed-State slice may add the complete bound Release Identity without accepting a caller-authored index SHA.

The stamped payload contains the complete generated JSON Schemas for State schemas `1` and `2`, the exact deterministic network-free `1 → 2` migration, the exact ten managed systemd units, and public no-authority qualification fixtures made by the real six-profile and seven-representation renderers. The migration changes only `schema_version`; it preserves every Owner value and secret, requests no new meaning, and forces regeneration and validation of release-bound configuration and subscriptions.

`go run ./cmd/sbxr-release -tag <tag> -commit <commit> -architecture <amd64|arm64> -output <application-archive>` remains the production application-archive build entry point. It refuses a commit other than the checked-out `HEAD`, refuses tracked changes, exports the exact committed source rather than building untracked files, builds the pure-Go Linux executable, generates all embedded material, and runs the exact native validators before it can write the application archive. The four-asset verifier, component manifest, staging, installation, and rollback contracts are implemented, but production component-archive creation remains blocked until the reviewed upstream distribution identities and pinned artifact provenance are canonical. An arbitrary local component directory is not accepted as provenance.

Native tools are release-build inputs, not Clean VPS prerequisites. On the Clean VPS, staging authenticates the immutable release, checks the exact embedded schema, zero-edge migration path, units, paths, baselines, qualified artifact hashes, executable identity, architecture, and runtime facts, and never executes the candidate.

Programs are reserved for `/opt/sbxr/releases/<Release Identity>/`; Owner and generated State stays under `/var/lib/sbxr/`; service-consumable secret material stays under `/etc/sbxr/`; and the active immutable subscription set stays at `/var/lib/sbxr/subscriptions/current/`. The one-file archive cannot write to any of those paths during staging.

The fixed bounds are 1 MiB for `release-index.json` and 256 MiB for each architecture archive. Changing either limit requires a reviewed specification and new qualification evidence.

Issue #127 adds the fresh-install coordination seam. `View` now hands one authenticated selected-architecture candidate to `PlanInstall`. The Plan accepts exactly one typed contribution from Network Policy, Connection Profiles, Cloudflare Tunnel, both Certificate Lifecycle lineages, and Subscription Publication, all bound to one Change Set and one complete candidate State. Its review discloses the exact Release Identity, file ownership, units, ports, firewall, Cloudflare and certificate effects, six profiles, seven representations, disk reservation, checks, interruption, cancellation, and rollback without rendering secrets.

Apply consumes that Plan once. The following recheck must return the same candidate and exact stable contribution facts, plus one root-verified Network Policy result; Software Lifecycle derives the fresh volatile digest itself. System Changes then owns the global lock, durable snapshot and journal, ordered steps, cancellation, health gates, State publication, post-publication agreement, rollback, restart recovery, and cleanup. State revision `1` is successful only after durable `Complete`. The approved inherited-executable-descriptor and private-Unix-socket sudo handoff is not yet implemented; `/usr/bin/sudo -v` is not the completed production path.

The Ubuntu install executor writes the authenticated application and component bytes beneath the exact versioned release directory, the fixed `/usr/local/bin/sbxr` symlink, and the exact ten embedded unit templates rendered only with that authenticated directory. Its rollback record is captured before mutation and can safely remove a verified partial activation without deleting a changed or unrelated target. Clean-VPS conflict classification remains in Network Policy, which checks the wider host, listener, firewall, provider, and ownership facts before this narrow file executor runs.

The Owner draft is fixed at `~/.local/state/sbxr/install-draft.json`. It contains only the allowlisted domain, email, selected public addresses, primary address, and ports as canonical JSON in an Owner-owned `0600` single-link file. Uncommitted secrets remain memory-only. Production session ownership and required discard on abandonment, disconnect, expiry, failed installation, or rollback remain part of the pending pasteable install entry.

The `sbxr-update-check.timer` service contract calls only Software Lifecycle's stable discovery behavior. Its focused command seam is implemented, but production wiring cannot yet obtain the installed verified sequence/schema proof because issue #127's pasteable install and completion receipt are still blocked. The installed proof and full four-asset production release must be completed there before this timer can perform a real Clean-VPS check; the current work does not claim that external run.

Issue #129 adds the reviewed Managed-to-Managed transaction seam. `PlanUpdate` accepts only the higher authenticated staged candidate, the exact current revision and State checksum, the complete `1 → 2` path, and the affected Connection Profiles, Cloudflare Tunnel, and Subscription Publication contributions. Apply consumes the Plan once, rechecks every bound fact after approval, verifies the prepared `N → N+1` State/release/migration binding, and hands one `Update` Change Set to System Changes. Xray, sing-box, cloudflared, subscription serving, code, components, units, schema, and migration switch in that one transaction; unchanged Network Policy and certificate resources receive no update step.

The Ubuntu update executor captures the exact prior versioned release, all ten units, and active executable link in the one root-only transaction snapshot. It writes the candidate beside the active release, atomically replaces units and `/usr/local/bin/sbxr`, verifies the candidate, and removes the prior release. Any full, partial, failed, cancelled, or restarted transaction can inspect and restore the exact captured bytes; durable System Changes cleanup removes the snapshot and journal. No history, blue-green listener stack, duplicate proxy service, in-place executable edit, unattended Apply, or second mutation authority is added.

Issue #130 adds only an explicit downgrade admission path. `View` freshly downloads, verifies, and stages the exact older tag selected by the Owner; it offers `Review downgrade` only when the selected identity differs, its authenticated sequence is lower, its updater schema is supported, and both releases use the currently publishable State schema `2` without a reverse migration. `PlanDowngrade` discloses the installed and selected Release Identities side by side with that compatibility result, then reuses the same one-use Managed transaction, prepared `N → N+1` State publication, health gates, rollback snapshot, restart recovery, and cleanup as `PlanUpdate`.

Stable discovery and `PlanUpdate` still reject lower sequences. A downgrade cannot select retained history, restore an old State revision or secret, or use an old snapshot or recovery parcel. The selected older release comes only from the fresh `View` verification; the prior release exists only inside the active transaction rollback snapshot and is deleted at durable `Complete`.

Issue #131 adds forward repair only for the current proven Desired State. `ViewRepair` reads a fresh System Changes inspection and hands out one protected repair candidate only for `Recovery Required` caused by valid current-State drift. A valid unfinished transaction instead offers only `Retry automatic rollback`. Missing or corrupt Desired State, lost secrets, a dead or replacement VPS, an older completed revision, and Owner regret offer secret-safe evidence plus separately confirmed Complete removal and Clean-VPS rebuild guidance; none can become repair authority.

`PlanRepair` consumes that observation once and accepts exactly one typed repair contribution from Connection Profiles, Cloudflare Tunnel, or Subscription Publication. The contribution binds the current revision and State checksum, fresh Observed State digest, exact reversible steps, required pre- and post-publication checks, disk reservation, and affected owning Module. Apply consumes the Plan once, repeats the observation and contribution after approval, accepts only State's unchanged-Owner-intent `N → N+1` prepared commit, and hands one `Repair` Change Set to System Changes. System Changes remains the only lock, Rollback Snapshot, journal, publisher, rollback, restart, and cleanup owner.

Repair never copies Observed State into Desired State, discovers resources for adoption, recreates a missing secret, selects history, restores an old revision, invents transaction material, force-unlocks, edits arbitrary files, or manually completes an unfinished Change Set. A successful repair advances the revision once because live resources and current intent were proved together; durable Complete deletes its temporary rollback material.

Issue #132 adds the rollback-safe half of Complete removal. `ViewCompleteRemoval` offers one protected candidate only from a fresh released-lock proof of Managed or Recovery Required with no unfinished rollback. `PlanCompleteRemoval` consumes it once and accepts only the exact Owner Console review plus Network Policy and Cloudflare Tunnel ownership proofs for the complete immutable inventory. Its secret-safe summary names every local and Cloudflare category, the Certificate Transparency and DNS-cache remnants, disk, ordinary sudo, cancellation boundary, token-revocation responsibility, exact starting status, rollback, and final Not installed proof. State binds either the exact valid current lineage or the exact raw bytes or absence that caused lineage-unavailable Recovery Required; it never invents a revision or checksum.

Apply requires the genuine interactively typed `COMPLETE REMOVAL` authority and the separate `Permanently remove SBXR` selection, rechecks every bound fact after approval, accepts only State's exact rollback binding, and hands one Complete-removal Change Set to System Changes. A valid lineage uses the unchanged-intent `N → N+1` binding; unavailable lineage uses the explicit raw-byte-or-absence binding. Public exposure and exact owned Cloudflare DNS, routes, and Tunnel are deleted and verified while rollback remains available. Only then is `Irreversible removal started` recorded immediately before Albert must revoke the scoped token. Issue #133 owns the forward-only token verification and final local deletion side. Production availability remains blocked by issue #127's inherited entry and release prerequisites.
