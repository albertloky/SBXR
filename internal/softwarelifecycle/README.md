# Software Lifecycle

Software Lifecycle owns SBXR release identity and delivery. One selected immutable tag either becomes one typed `VerifiedRelease` and one completely staged architecture payload, or `View` returns `SOFTWARE-LIFECYCLE-RELEASE-REFUSED` with no candidate or permitted mutation.

The genuine external Seam is `ReleaseSource`. The GitHub Adapter:

1. uses public GitHub HTTPS with no GitHub login, personal token, or installed GitHub CLI;
2. resolves the exact tag commit, requires one immutable release containing exactly `install.sh`, `release-index.json`, and the four fixed architecture archives, and fetches its one GitHub release attestation;
3. verifies the signed bundle with `sigstore-go` `1.3.0`, one RFC 3161 timestamp, exact `https://dotcom.releases.github.com` identity, and the source-controlled GitHub trusted-root SHA-256 `26B3382D5700AFBCD84F980D1D5B6C52BFF743DC2A8EE86B8B44C8E1245CE485`;
4. downloads every asset through bounded public HTTPS, stopping before more than 1 MiB for `release-index.json` or 256 MiB for another asset can enter memory, and requires exact equality among GitHub's immutable asset metadata, the signed subjects, the index, and the downloaded bytes; and
5. returns only the repository, tag, commit, six asset digests, downloaded bytes, and verifier proof needed by `View`.

Raw verifier output and errors never cross the Adapter. `View` requires the attested, indexed, verified, and downloaded sets to agree exactly. The v1 index accepts only its ten named top-level fields and the four named fields for each of exactly four roles: two application archives and two matching offline component archives. Version and tag remain safe opaque strings; sequence, not version parsing, controls ordering. It rejects duplicate JSON keys, unknown fields, missing or duplicate roles/names, unsafe names, source ZIPs, malformed values, non-positive or oversized files, digest/size disagreement, extra or missing files, application archives that do not contain exactly one regular executable named `sbxr` with mode `0755`, unsafe or incomplete component manifests, and trailing gzip members.

`View` reports only installation status, installed identity when valid, verified and staged candidate proof, migration schema summary, eligibility, the five indexed release assets, and currently permitted review action. It does not publish or execute an archive, change product State or the host, retain release history, expose Owner-managed values, or accept ordinary HTTPS/checksums/earlier proof.

Issue #128 adds one update-discovery path to that same `View`. The default asks GitHub only for the current stable release. Drafts and unintended prereleases are ignored; an alternate tag must be explicitly reviewed and cannot silently cross to another tag. `View` verifies the selected release through the exact six-asset public proof, accepts only a different Release Identity with a higher authenticated sequence, a compatible updater/index schema, and either the installed State schema or one complete sequential no-network forward migration path embedded identically in both application archives. It then offers only `Review update`. It never stages, extracts, executes, migrates, applies, or approves a discovered candidate.

Outside a transaction, the Ubuntu Adapter stores at most one newest verified unapplied candidate in `/var/lib/sbxr/software-lifecycle/update-candidate.tar`. A lock on the verified directory makes the sequence comparison and atomic replacement one operation, so overlapping checks cannot leave an older candidate. Replacement changes one root-owned `0600` file beneath a root-owned `0700` directory whose complete parent chain is non-linked, correctly owned, and not group/world-writable; an interrupted `.next` file is discarded on restart. The retained evidence is bounded and reverified byte-for-byte before `View` reports it. An older discovery cannot replace it, and there is no previous-release list or history browser.

Issue #126 lets `View` authenticate one selected architecture before the Ubuntu staging Adapter opens it in a fresh private directory. The Adapter never executes the candidate. It checks archive size, digest, entry type, ownership and mode, Linux ELF architecture, static linkage, Go `1.26.5`, `GOOS=linux`, selected `GOARCH`, and `CGO_ENABLED=0`, then removes the temporary copy.

The executable embeds repository, immutable tag, commit SHA, and the SHA-256 of its unstamped ELF bytes as its independent payload identity. A later installed-State slice may add the complete bound Release Identity without accepting a caller-authored index SHA.

The stamped payload contains the complete generated JSON Schemas for State schemas `1` and `2`, the exact deterministic network-free `1 → 2` migration, the exact eleven managed systemd units including restart recovery, and public no-authority qualification fixtures made by the real six-profile and seven-representation renderers. The migration changes only `schema_version`; it preserves every Owner value and secret, requests no new meaning, and forces regeneration and validation of release-bound configuration and subscriptions.

`go run ./cmd/sbxr-release -tag <tag> -commit <commit> -architecture <amd64|arm64> -output <application-archive> -component-output <component-archive>` is the one production release-build entry point. It refuses a commit other than the checked-out `HEAD`, refuses tracked changes, exports the exact committed source rather than building untracked files, builds the pure-Go Linux executable, and builds the matching component archive from the strict repository-owned source manifest. The manifest pins the reviewed official Xray-core, sing-box, cloudflared, complete Certbot wheel closure, and qualification-only Mihomo `v1.19.29` by source, version, architecture, filename, size, SHA-256, and HTTPS URL. The builder accepts no caller component root, source URL, command, script, package-manager behavior, or destination. It verifies and safely extracts every source, runs the native validators, removes Mihomo before assembling the runtime component archive, qualifies both outputs before publishing either, and removes a newly written application output if the component output cannot be created.

`go run ./cmd/sbxr-release bootstrap -version <version> -sequence <sequence> -tag <tag> -commit <commit> -output <install.sh>` generates the one release-specific Pasteable Install Command. It embeds the exact repository, tag, commit, version, sequence, supported architectures, and six names. It does not embed the index digest because the index binds the complete `install.sh` bytes; doing both would create a circular digest. GitHub HTTPS supplies the index from the script's immutable release. The script then requires Ubuntu Server 24.04, `amd64` or `arm64`, fixed root-owned Ubuntu foundation tools, and a real terminal. Root may update APT metadata and install or repair only `ca-certificates`, `curl`, `iproute2`, `nftables`, `iptables`, `sudo`, and their required Ubuntu foundation. A root-owned active link is re-entered only when its exact release path, index digest, executable metadata, architecture, and repository/tag/commit agree; the executable rechecks that it remains active before selecting Managed or Recovery Required. A pre-activation install instead uses the root-owned, secret-free recovery receipt only when it agrees with the freshly authenticated release index and executable; its privileged recovery still validates the complete protected transaction. Otherwise the script opens Not installed. Root starts the complete Owner Console directly. A non-root Owner Launch Identity authenticates before the same complete root Owner Console starts. Temporary material is cleaned on success, refusal, or interruption. Its only public failures are fixed bootstrap codes.

`go run ./cmd/sbxr-release index -version <version> -sequence <sequence> -tag <tag> -commit <commit> -directory <asset-directory> -output <release-index.json>` is the only index-build path. It requires the directory to contain exactly `install.sh` and the four fixed application/component archive names as regular files, calculates their sizes and SHA-256 values itself, obtains schema facts from the same embedded release metadata, and creates one exclusive strict index. The manually dispatched `Mint immutable candidate` workflow runs the two native Ubuntu 24.04 architecture builders, executes each packaged application on its matching architecture, generates the exact bootstrap, combines only those five outputs into the index, runs the complete automated suite and marker scan, and produces the exact six-file candidate artifact. Publication occurs only after an Owner-authenticated read-only check proves immutable releases enabled. Publishing the prerelease automatically runs the production public HTTPS and Sigstore verifier, exact six-asset checks, both architecture staging paths, package suite, production package seams, and marker scan. For one exact ADR-0010 root-runtime identity, `go run ./cmd/sbxr-release acceptance` reopens and binds those unchanged six bytes into one redacted Acceptance Record. It marks Integrated Ubuntu Verification, Codex Live Acceptance, and Owner Acceptance `Not required` and does not claim that evidence. Stable publication runs from the exact release commit, byte-compares the retained record with the release body, reverifies the bytes, proves latest and pinned bootstrap equality, scans the public assets, and reruns the public bootstrap package gates before README activation. Automatic discovery admits the stable identity only when its durable record agrees with the immutable release metadata and downloaded index. Release `v1.0.6` is the current predecessor identity; it cannot update to the root-runtime design.

Native tools are release-build inputs, not Clean VPS prerequisites. On the Clean VPS, staging authenticates the immutable release, checks the exact embedded schema, zero-edge migration path, units, paths, baselines, qualified artifact hashes, executable identity, architecture, and runtime facts, and never executes the candidate.

Programs are reserved for `/opt/sbxr/releases/<Release Identity>/`; Owner and generated State stays under `/var/lib/sbxr/`; service-consumable secret material stays under `/etc/sbxr/`; and the active immutable subscription set stays at `/var/lib/sbxr/subscriptions/current/`. The one-file archive cannot write to any of those paths during staging.

The fixed bounds are 1 MiB for `release-index.json` and 256 MiB for each architecture archive. Changing either limit requires a reviewed specification and new qualification evidence.
